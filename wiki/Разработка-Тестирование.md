# Разработка-Тестирование

Проверяйте затронутые backend, frontend и Compose-конфигурацию до передачи изменения. CI для pull request использует path filter: если компонент не изменялся, соответствующая проверка может быть пропущена. Локальная проверка остаётся обязанностью автора изменения.

## Backend

1. Из каталога `backend` загрузите модули при первом запуске.

   ```bash
   go mod download
   ```

2. Выполните тесты.

   ```bash
   go test ./...
   ```

3. Для проверки, близкой к CI, добавьте race detector, покрытие и таймаут.

   ```bash
   go test ./... -race -coverprofile=coverage.out -covermode=atomic -timeout 5m
   go tool cover -func=coverage.out
   ```

Проверьте результат: `go test` завершается с кодом 0. Во втором варианте создаётся `coverage.out`, а последняя команда печатает итог покрытия. Не добавляйте этот файл в коммит.

CI дополнительно запускает `golangci-lint` версии, зафиксированной workflow. Если изменён backend, выполните эквивалентную проверку установленным в проекте линтером или дождитесь CI; не подменяйте её произвольным набором `go vet`.

## Frontend

1. Из каталога `frontend` установите зависимости без изменения lock-файла.

   ```bash
   npm ci
   ```

2. Запустите lint, typecheck и тесты.

   ```bash
   npm run lint
   npx tsc --noEmit
   npm test
   ```

3. Для изменения сборки выполните production-сборку.

   ```bash
   npm run build
   ```

Проверьте результат: каждая команда завершается с кодом 0, а `npm run build` создаёт frontend-сборку без ошибки TypeScript или Vite. Не коммитьте `frontend/dist` и `frontend/node_modules`.

## Docker и workflow

Проверьте Docker Compose до запуска:

```bash
docker compose config
```

Проверьте образы без запуска:

```bash
make build
```

Проверьте результат: `docker compose config` выводит объединённую валидную конфигурацию, а сборка завершает каждый образ без ошибки. Для изменения production overlay выполните также `make build-prod`.

Workflow PR запускает Hadolint для Dockerfile, actionlint для workflow-файлов и собирает образы для сканирования Trivy, если изменены соответствующие пути. Изменение `.github/workflows/wiki.yml` попадает в проверку actionlint через путь `.github/workflows/**`.

Проверьте результат: после push проверка `Security / actionlint` в PR не имеет ошибки. Локальная проверка YAML не заменяет выполнение workflow на GitHub.

## Выбор проверки

| Изменение | Минимальная локальная проверка |
|---|---|
| `backend/internal/domain` | Тесты изменённого пакета и `go test ./...` перед передачей |
| API или SQL-репозиторий | Backend-тесты и ручной запрос к локальному серверу с PostgreSQL/Redis |
| Парсер | `go test ./internal/parser` и загрузка минимального отчёта |
| Миграция | Чистая БД, запуск сервера, проверка схемы и целевого сценария |
| `frontend/src` | `npm run lint`, `npx tsc --noEmit`, `npm test`, при изменении сборки — `npm run build` |
| Dockerfile/Compose | `docker compose config`, релевантная сборка образа |
| Workflow | Проверка actionlint в PR; для Wiki — тестовый ручной запуск после настройки токена |
| Wiki | Проверка H1, Wiki-ссылок и статического Markdown; после merge — результат workflow публикации |
