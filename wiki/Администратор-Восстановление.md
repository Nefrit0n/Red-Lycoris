# Администратор-Восстановление

Восстановление заменяет состояние выбранной БД содержимым копии. Используйте доверенный архив и сначала выполните [проверку резервной копии](Администратор-Резервное-копирование). Код приложения и файлы миграций должны соответствовать восстанавливаемой ревизии: запуск нового backend поверх старой копии сразу применит новые миграции.

## Ограничения restore.sh

Нельзя описывать текущий `ops/backup/restore.sh` как гарантированно работающую команду восстановления всей установки.

| Участок | Реализация и последствие |
| --- | --- |
| PostgreSQL | Завершает подключения, удаляет и пересоздаёт БД, выполняет `pg_restore --no-owner --no-privileges --exit-on-error` |
| Подстановка имени БД | SQL использует `:'dbname'` и `:"dbname"` в аргументе `psql -c`. Этот режим передаёт SQL серверу без подстановки переменных psql; ожидается синтаксическая ошибка до удаления БД |
| Redis AOF | Запрещает простую замену RDB при работающем Redis с `appendonly=yes`, но проверяет это после восстановления PostgreSQL |
| Остановленный Redis | Проверка AOF пропускается; это не делает замену снимка безопасной |
| Запуск приложения | Использует `docker compose start`, а не `up`: на чистой установке не создаёт отсутствующие контейнеры |
| Ошибка в середине | Нет автоматического отката БД или гарантированного возврата сервисов в прежнее состояние; обработчик завершения удаляет только временный каталог |

Вывод о `psql -c` основан на командах скрипта и [режимах выполнения psql 16](https://www.postgresql.org/docs/16/app-psql.html). Ниже SQL передаётся через stdin, где подстановка поддерживается. Скрипт приложения этой документацией не изменяется.

| Параметр restore.sh | Назначение |
| --- | --- |
| Позиционный путь к архиву | Обязателен |
| `--yes`, `-y` | Убирает интерактивное подтверждение; не выполняет дополнительные проверки безопасности |
| `--no-redis` | Не восстанавливает и не очищает Redis; прежнее содержимое остаётся |
| `--skip-readiness` | Не ожидает `/readyz`; успешный выход не подтверждает готовность |
| `--readiness-timeout` | По умолчанию `120` секунд |
| `POSTGRES_USER`, `POSTGRES_DB` | По умолчанию `redlycoris` |
| `API_PORT` | По умолчанию `8080` |
| `APP_SERVICES` | По умолчанию backend и имена отсутствующих в корневом Compose worker-сервисов; frontend в список не входит |

## Область ручной процедуры

Следующая процедура воспроизводит восстановление PostgreSQL из артефакта скрипта, исправляя способ ввода SQL. Она не объявляет Redis восстановленным. Для полного восстановления очереди необходима отдельная проверенная RDB/AOF-процедура; см. ограничения в конце страницы.

Команды предназначены для Bash на Linux. Выполняйте их по шагам и прекращайте выполнение при любой ошибке. Файлы `.env` и Compose должны принадлежать целевой установке; для скриптов `.env` должен быть доверенным и совместимым с Bash.

## На чистой установке

1. Подготовьте исходники, `.env` и образы той же ревизии, что была сохранена вместе с копией. Проверьте архив через `verify.sh` до запуска основного приложения.
2. Выберите набор Compose-файлов. Пример для корневого production overlay:

   ```bash
   export COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml
   docker compose config --quiet
   docker compose up -d --no-build postgres redis
   docker compose exec -T postgres sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
   docker compose exec -T redis redis-cli PING
   ```

3. Не запускайте backend до восстановления БД: иначе появятся миграции и bootstrap-пользователь, которых не должно быть в пустой базе назначения для `pg_restore`. Перейдите к общей процедуре ниже.

Проверка результата: PostgreSQL принимает подключения, Redis отвечает `PONG`, backend ещё не запущен. Наличие пустого Redis означает отсутствие восстановленной очереди, а не успешное восстановление её снимка.

## Поверх существующей установки

Предупреждение: все изменения PostgreSQL после момента копии будут потеряны при замене БД. Отдельно сохраните проверенную копию текущего состояния и старые образы, чтобы возврат оставался возможным. Не выполняйте `make clean` и не удаляйте тома.

1. Закройте внешний доступ и остановите запись, включая сторонние клиенты БД. Проверьте, что выбраны нужные Compose-файлы и проект:

   ```bash
   docker compose config --quiet
   docker compose ps
   docker compose stop frontend backend
   docker compose exec -T postgres sh -c 'printf "database=%s user=%s\n" "$POSTGRES_DB" "$POSTGRES_USER"'
   docker inspect redlycoris-postgres --format '{{json .Mounts}}'
   docker inspect redlycoris-redis --format '{{json .Mounts}}'
   ```

2. Проверьте архив отдельно, не изменяя основную БД. Определите план для Redis до замены PostgreSQL: старый кэш и очередь могут не соответствовать восстанавливаемому состоянию.

Проверка результата: приложение остановлено, хранилища идентифицированы, текущая копия сохранена, выбранный архив прошёл проверку PostgreSQL. Без решения по Redis не переходите к публикации восстановленной установки.

## Общая процедура PostgreSQL

1. Задайте путь к уже проверенному архиву и извлеките только дамп в закрытый временный каталог:

   ```bash
   umask 077
   RECOVERY_ARCHIVE=/путь/к/redlycoris-архив.tar.gz
   test -f "$RECOVERY_ARCHIVE"
   RECOVERY_TMP="$(mktemp -d)"
   tar -xOf "$RECOVERY_ARCHIVE" ./pgdump.bin > "$RECOVERY_TMP/pgdump.bin"
   test -s "$RECOVERY_TMP/pgdump.bin"
   docker compose cp "$RECOVERY_TMP/pgdump.bin" postgres:/tmp/redlycoris-restore-pgdump.bin
   docker compose exec -T postgres pg_restore --list /tmp/redlycoris-restore-pgdump.bin
   ```

   Проверка этого шага: файл непустой, `pg_restore --list` выводит состав дампа без ошибок. Убедитесь, что присутствуют схема приложения и `schema_migrations`.

2. Ещё раз сопоставьте имя БД с планом восстановления. Следующая команда необратимо удаляет выбранную БД и завершает её подключения. Она допустима только после проверки текущей копии и остановки всех писателей; на чистой установке будет удалена пустая БД, созданная образом PostgreSQL.

   ```bash
   docker compose exec -T postgres sh -c 'exec psql -X -v ON_ERROR_STOP=1 -v dbname="$POSTGRES_DB" -U "$POSTGRES_USER" -d postgres' <<'SQL'
   SELECT pg_terminate_backend(pid)
   FROM pg_stat_activity
   WHERE datname = :'dbname' AND pid <> pg_backend_pid();
   DROP DATABASE IF EXISTS :"dbname";
   CREATE DATABASE :"dbname";
   SQL
   ```

   Проверка этого шага: вывод содержит `DROP DATABASE` и `CREATE DATABASE`, нет сообщений ERROR. При ошибке не продолжайте восстановление поверх неопределённого состояния.

3. Восстановите дамп:

   ```bash
   docker compose exec -T postgres sh -c 'exec pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --no-privileges --exit-on-error /tmp/redlycoris-restore-pgdump.bin'
   docker compose exec -T postgres sh -c 'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version, dirty FROM schema_migrations; SELECT count(*) AS projects FROM projects; SELECT count(*) AS users FROM users; SELECT count(*) AS findings FROM findings;"'
   ```

Проверка результата: `pg_restore` завершился с кодом `0`, версия схемы соответствует копии, `dirty=f`, контрольные количества совпадают с журналом проверки архива. Владельцы и привилегии исходной БД не восстанавливаются этими флагами. Если `pg_restore` прервался, база могла восстановиться частично: не запускайте приложение; устраните причину и повторите замену БД из проверенной копии.

## Redis и условия возврата в работу

По умолчанию в поставке включён AOF, а архив содержит только RDB. `--no-redis` оставляет прежний Redis как есть; остановка Redis перед запуском скрипта лишь обходит проверку и может привести к загрузке прежнего AOF вместо RDB. Не используйте эти действия как способ восстановления.

При полном восстановлении должны быть согласованы PostgreSQL, кэш и очередь `enrichment:pending`. Если выбрано восстановление только PostgreSQL с новым пустым Redis, сохраните старый том отдельно и явно зафиксируйте потерю состояния очереди и кэша. Такой вариант требует решения о повторной обработке находок; он не эквивалентен восстановлению RDB. Штатный `enrich-all` выбирает только находки без строки в `finding_scores`, а не восстанавливает произвольное содержимое прежней очереди.

### Проверка приложения после согласованного восстановления

1. Только после проверки PostgreSQL и выполнения выбранного плана Redis создайте или запустите приложение из сохранённых образов:

   ```bash
   docker compose up -d --no-build backend frontend
   docker compose logs --tail=100 backend
   curl --fail --silent --show-error http://localhost:8080/readyz
   curl --fail --silent --show-error http://localhost:8080/api/v1/version
   docker compose exec -T redis redis-cli XINFO GROUPS enrichment:pending
   docker compose exec -T redis redis-cli XPENDING enrichment:pending enrichment-workers
   ```

2. Выполните вход, откройте контрольный проект, находку и историю изменений. Повторно проверьте `schema_migrations` SQL-командой выше. Рассмотрите отзыв восстановленных сессий и токенов по регламенту инцидента: копия содержит состояние доступа на момент её создания.

Проверка результата: `/readyz` возвращает `status: ready`, версия приложения соответствует выбранной ревизии, миграции не находятся в состоянии dirty, контрольные данные доступны. Состояние Redis соответствует выбранному плану, а не только отвечает на PING. Только после этого открывайте внешний доступ. Закрытый временный дамп на узле и `/tmp/redlycoris-restore-pgdump.bin` в контейнере содержат чувствительные данные; удалите именно эти файлы по регламенту после завершения проверки, не затрагивая исходный архив.
