# Система-Модель-безопасности

Платформа защищает доступ к находкам и проектам через пользовательские сессии, проектные роли и отдельные API-токены. База содержит чувствительные сведения: результаты сканирования, фрагменты кода, параметры репозиториев, пользователей и журнал действий. Контроль доступа приложения не защищает эти данные от администратора PostgreSQL, владельца узла или лица с доступом к резервным копиям.

## Границы доверия

| Граница | Реализованная защита | Чего она не обеспечивает |
|---|---|---|
| Клиент → API | Аутентификация и проверки доступа в middleware/обработчиках | API слушает HTTP; TLS не настраивается самим сервером |
| Проект → пользователь | `user_project_roles` и глобальная роль администратора | Не изоляция отдельных арендаторов; дедупликация глобальна |
| Пароль → хранилище | Argon2id с индивидуальной солью | Не шифрование данных приложения и не защита от уже скомпрометированного сервера |
| Токен → хранилище | Хеширование случайного секрета | Похищенный исходный токен остаётся пригодным до отзыва/истечения |
| Отчёт сканера → находка | Парсер и проверки обработчика | Не гарантия отсутствия секретов во всех свободных текстовых полях |
| Событие → аудит | Запись запросов и отдельных прикладных действий | Не неизменяемый, криптографически заверенный журнал |

## Пароли

`auth.Hash` и `auth.Verify` используют библиотеку `alexedwards/argon2id`. Bcrypt в этих функциях не используется.

| Параметр Argon2id | Значение в коде |
|---|---:|
| Память | 65 536 KiB |
| Итерации | 3 |
| Параллелизм | 2 |
| Длина соли | 16 байт |
| Длина ключа | 32 байта |

Вход нормализует email удалением крайних пробелов и приведением к нижнему регистру. Пароль проверяется по `users.password_hash`; пользователь должен иметь `is_active = true`. Дополнительная таблица `user_credentials` не заменяет этот источник хеша при входе.

При смене собственного пароля обработчик проверяет текущий пароль, требует не менее восьми символов нового пароля после удаления крайних пробелов, меняет хеш, снимает требование смены и отзывает прежние сессии. Затем создаёт новую сессию. Эти операции не объединены одной транзакцией, поэтому успешность каждого шага имеет значение.

### Первоначальная и принудительная смена

Сессия загружает `user_credentials.must_change`; при установленном флаге middleware не допускает пользователя к основным защищённым маршрутам до смены пароля. Отдельные маршруты аутентификации находятся вне этой группы.

Bootstrap создаётся только при пустой таблице `users`. Параметр `BOOTSTRAP_ADMIN_FORCE_PASSWORD_CHANGE` читается конфигурацией, но `ensureBootstrapAdmin` лишь записывает его значение в лог: запись `user_credentials` и установка `must_change` этим путём не выполняются. Следовательно, одного значения `true` недостаточно, чтобы гарантировать принудительную смену пароля созданного bootstrap-пользователя. Миграционное заполнение credentials для уже существовавших пользователей — другой путь, оно не повторяется автоматически после создания bootstrap.

## Сессии

Сессия — непрозрачный случайный токен, **не JWT**. Генератор использует 32 случайных байта и кодирует их в hex. В БД хранится SHA-256 токена, а не его исходное значение.

| Свойство | Реализация |
|---|---|
| Cookie | `rl_session` |
| `HttpOnly` | `true` |
| `Secure` | Значение `COOKIE_SECURE` |
| `SameSite` | `Lax` |
| `Path` | `/` |
| `Domain` | Не задаётся |
| `MaxAge` | Длительность сессии в секундах |
| Проверка запроса | Хеш токена, отсутствие отзыва, `expires_at > now()`, активность пользователя |
| Обновление активности | `last_used_at` обновляется при валидации |
| Выход | Отзыв серверной сессии и удаление cookie |
| Очистка | Сервер ежечасно удаляет истёкшие и отозванные сессии |

По умолчанию конфигурация задаёт `SESSION_DURATION=168h`. `COOKIE_SECURE` по умолчанию зависит от `ENV`: выключен при `dev`, включён при любом другом значении. В `env.example` явно задано `COOKIE_SECURE=false`; этот пример нельзя считать готовой настройкой HTTPS-развёртывания. Кроме того, файл `.env` Compose не передаёт автоматически каждую переменную в контейнер: важен итоговый раздел `environment`.

Обычный сессионный токен может передаваться через Bearer, если cookie отсутствует. Однако PAT распознаётся middleware отдельно, раньше обычной загрузки сессии; сочетание PAT и cookie не следует считать способом объединения прав.

Refresh продлевает срок той же серверной сессии, если осталось менее 24 часов. Исходный токен не заменяется, а HTTP-обработчик refresh не переустанавливает cookie. Поэтому продление в БД не равнозначно продлению `MaxAge` в браузере.

## API-токены

PAT имеет вид `rl_pat_<prefix>_<secret>`. Секрет генерируется из 32 случайных байт, в БД сохраняется его SHA-256; middleware сравнивает хеши через `subtle.ConstantTimeCompare`. Выбор токена проверяет срок и отсутствие отзыва.

Токен привязан к одному проекту. Загрузка скана требует scope `scans:write` и получает проект из токена. В текущем коде нет универсального CI-токена и выбора проекта по `project_key`.

Проверка PAT не загружает пользовательскую сессию и не проверяет активность создателя токена. Отзыв пользовательских сессий сам по себе не отзывает PAT. При компрометации учётной записи необходимо отдельно учитывать её токены. Само наличие значения в `scopes` не означает, что произвольный маршрут применяет его: scope проверяется только там, где это явно предусмотрено middleware или обработчиком.

## Фактический RBAC

| Уровень | Основные полномочия |
|---|---|
| Глобальный администратор | Администрирование пользователей и аудит; обход проектной проверки; ручная синхронизация источников и массовое обогащение |
| `viewer` проекта | Чтение проекта, находок, обогащений, истории, сканов |
| `triager` проекта | Права viewer, импорт, изменение статуса, закрытие/открытие, назначение, комментарии и обогащение находки |
| `project_admin` | Права triager, изменение проекта, управление участниками и API-токенами, удаление находок |
| Владелец проекта или глобальный администратор | Удаление проекта; одной роли `project_admin` недостаточно |

Таблица отражает основные проверки, а не заменяет контракт каждого обработчика. Например, создание проекта доступно аутентифицированному пользователю, а сохранённые представления имеют собственную проверку владельца.

Проектные проверки читают `user_project_roles`. Таблицы `groups`, `user_groups`, `project_access`, `roles`, `permissions`, `role_permissions` присутствуют, но не образуют единый исполняемый механизм авторизации всех API. Членство в группе и строка `project_access` не подменяют проектную роль, которую читает middleware. Каталожные роли `auditor` и `viewer` не дают универсальной глобальной модели доступа только своим наличием.

Схема не содержит отдельного арендатора, а уникальный fingerprint действует между проектами. О последствиях для повторного импорта см. [дедупликацию](Система-Дедупликация).

## Сетевая защита и вход

`TRUST_PROXY=false` использует `RemoteAddr` для IP клиента. При `true` выбирается первый элемент `X-Forwarded-For`, без проверки адреса отправившего прокси по доверенной подсети. Прямой доступ к такому API позволяет клиенту влиять на IP в ограничении входа и аудите. Завершающий доверенный прокси должен формировать заголовок сам, а прямой маршрут в обход него должен быть закрыт.

`CORS_ORIGINS` формирует список разрешённых origin. Middleware добавляет `Access-Control-Allow-Origin` при точном совпадении; сам запрос от другого origin не отклоняется сервером. CORS не является авторизацией. Отдельной проверки CSRF-токена в маршрутах и middleware нет; cookie использует `SameSite=Lax`.

Ограничение входа хранит счётчик Redis для пары IP и нормализованного email: после пяти запросов в 15-минутном окне следующие блокируются до окончания окна, успешный вход сбрасывает счётчик. При ошибке Redis ограничение пропускает запрос. Поля `failed_attempts` и `locked_until` существуют в credentials, но обычный `Login` не использует их для блокировки.

Сетевые ограничения, TLS и доступ к служебным маршрутам требуют отдельной настройки: [безопасная сетевая конфигурация](Администратор-Безопасная-сетевая-конфигурация).

## Аудит и чувствительные данные

Middleware записывает метод, путь, полный URI запроса, статус, длительность, пользователя и сессию при наличии, сведения о ресурсе, User-Agent и производные признаки риска. IPv4 маскируется заменой последнего октета на `x`; это не универсальное обезличивание IP, в частности IPv6 остаётся без такого преобразования. Полный URI может содержать чувствительные query-параметры.

Из общего HTTP-аудита исключены HEAD, OPTIONS, маршруты `/api/v1/auth/` и поток просмотра аудита. Обработчики входа и выхода не добавляют отдельную запись через этот writer. Следовательно, журнал не является полным журналом всех попыток аутентификации.

Writer использует канал в памяти; при заполнении запускает дополнительную goroutine записи. Ошибки записи не возвращаются инициатору действия и в writer игнорируются. Аварийное завершение процесса может потерять ожидающие записи. Общий middleware выводит изменения создания/удаления из маршрута, а не вычисляет полный diff каждой изменённой строки.

Колонки `integrity_hash`, `integrity_prev_hash` и `integrity_verified` предусмотрены схемой, но цепочка хешей и проверка целостности не вычисляются штатным writer. Наличие этих колонок не делает журнал защищённым от модификации администратором БД. Аналогично наличие полей TOR/VPN/страны не означает выполнение сетевой атрибуции.

Парсеры Gitleaks и TruffleHog хешируют отдельное значение секрета для группировки и формируют маскированное представление. Это не универсальный фильтр всех секретов: описания, snippets, evidence и данные других форматов могут содержать исходные чувствительные сведения. Хеш секрета не шифрует эти поля. На уровне приложения нет общего шифрования содержимого находок в БД.

## Ограничения реализации

| Область | Граница текущего кода |
|---|---|
| OIDC, LDAP/AD, SSO | Допустимые значения в `user_identities` не сопровождаются соответствующим потоком входа |
| MFA | Таблица и отображаемый признак не сопровождаются проверкой фактора при входе |
| Изоляция | Проекты не являются независимыми арендаторами; глобальный администратор и глобальный fingerprint пересекают проектные границы |
| Защита хранилища | Доступ к узлу, PostgreSQL, Redis и резервным копиям контролируется инфраструктурой, не RBAC интерфейса |
| Подтверждение действий | Аудит не является атомарной частью каждой прикладной транзакции |
