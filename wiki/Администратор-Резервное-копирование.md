# Администратор-Резервное-копирование

Поставка содержит `ops/backup/backup.sh` для создания архива и `verify.sh` для проверки в отдельном временном окружении. Архив не включает всё, что необходимо для восстановления узла.

## Состав копии

| Артефакт | Содержание |
| --- | --- |
| `pgdump.bin` | `pg_dump --format=custom --compress=9` всей выбранной БД: данные приложения, схема, локальные базы обогащения, пользователи и сессии |
| `redis.rdb` | Необязательный снимок через `BGSAVE`, затем копирование `/data/dump.rdb` |
| `manifest.json` | `version`, `created_at`, список `artifacts` с именем, размером и SHA-256 |

В архив не включаются образы, исходники, `.env`, Compose-overlay, сертификаты и ключи прокси, внешняя конфигурация узла, Docker-журналы и файлы Redis AOF. Сохраните их отдельно по правилам вашего контура. Архив не шифруется и не подписывается скриптом; контрольные суммы не подтверждают доверенное происхождение копии.

Имя архива имеет вид `redlycoris-ГГГГ-ММ-ДД-ЧЧММСС.tar.gz`. Поле версии по умолчанию жёстко задано в скрипте как `0.1.0b`, поэтому передавайте `APP_VERSION` по фактически работающей сборке, а не полагайтесь на значение скрипта.

## Параметры скриптов

| Скрипт | Параметр | Значение и действие |
| --- | --- | --- |
| `backup.sh` | `--destination` | Обязательный каталог назначения |
| `backup.sh` | `--retention-days` | По умолчанию `7`; удаляет совпадающие архивы через `find -mtime +N -delete` |
| `backup.sh` | `--include-redis` / `--no-redis` | Включить/исключить RDB; по умолчанию включён |
| `verify.sh` | Позиционный путь к архиву | Обязателен |
| `verify.sh` | `--no-redis` | Пропустить проверку RDB |
| `verify.sh` | `--postgres-image`, `--redis-image` | По умолчанию `postgres:16-alpine`, `redis:7-alpine` |
| `verify.sh` | `--timeout` | По умолчанию `120` секунд ожидания готовности временных сервисов; не общий предел времени `pg_restore` |

Нужны Bash, Docker с Compose plugin, `python3`, `tar` и стандартные утилиты оболочки. Python-часть читает артефакты целиком для вычисления хеша: предусмотрите память не только для БД, но и для проверки больших файлов. Временный PostgreSQL проверки размещается в `tmpfs`.

## Подготовка окружения скриптов

Скрипты выполняют `source .env` из текущего каталога. Файл должен быть доверенным Bash-совместимым файлом присваиваний, а не произвольным документом Compose: значения с пробелами заключайте в кавычки. `source` исполняет содержимое файла. Не используйте присланный извне `.env` без проверки и не выводите секреты в журнал.

1. Перейдите в корень нужной установки. На Linux передайте набор Compose-файлов через окружение, поскольку скрипты не принимают собственный параметр `-f`:

   ```bash
   export COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml
   docker compose config --quiet
   docker compose ps
   command -v docker python3 tar
   ```

   Если есть локальные overlay, добавьте их в том же порядке; для базовой установки задайте только `docker-compose.yml`. Сохраните то же имя проекта Compose. Разделитель `:` здесь относится к Linux; см. [переменные Compose](https://docs.docker.com/compose/how-tos/environment-variables/envvars/).

2. Сопоставьте PostgreSQL и Redis с целевой установкой и проверьте права на каталог копий. Не продолжайте при неизвестном проекте или неожиданном наборе сервисов.

Проверка результата: конфигурация корректна, `ps` показывает нужные контейнеры, инструменты найдены. При проверке архива используйте доверенные образы, соответствующие версии основных хранилищ.

## Создание согласованной копии

Предупреждение: `backup.sh` после создания архива удаляет старые файлы `redlycoris-*.tar.gz` в каталоге назначения. `--retention-days 0` не отключает удаление. Выберите отдельный каталог и срок хранения до запуска. Скрипт также не останавливает приложение автоматически; без остановки записи снимки PostgreSQL и Redis относятся к разным моментам.

1. Закройте внешний приём данных, согласуйте перерыв и остановите все процессы записи. Для корневого Compose:

   ```bash
   docker compose stop frontend backend
   docker compose ps
   ```

   PostgreSQL и Redis должны оставаться запущенными. Исключите параллельные CLI-операции и сторонних писателей в БД.

2. Выберите доступный администратору каталог на хранилище копий. Следующий путь — пример, замените его своим:

   ```bash
   umask 077
   BACKUP_DESTINATION="/srv/redlycoris-backups/$(date -u +%Y%m%dT%H%M%SZ)"
   export APP_VERSION="$(tr -d '[:space:]' < VERSION)"
   bash ops/backup/backup.sh --destination "$BACKUP_DESTINATION" --retention-days 7
   ```

   Используйте `VERSION` только после проверки, что рабочая копия соответствует запущенному образу. Если `.env` содержит `APP_VERSION`, скрипт может переопределить экспортированное значение — проверьте манифест.

3. Сохраните путь, напечатанный скриптом. Проверьте архив, заменив пример реальным именем:

   ```bash
   tar -tzf /путь/к/redlycoris-архив.tar.gz
   tar -xOf /путь/к/redlycoris-архив.tar.gz ./manifest.json
   ```

4. После успешной копии верните приложение в работу:

   ```bash
   docker compose start backend frontend
   curl --fail --silent --show-error http://localhost:8080/readyz
   ```

Проверка результата: скрипт завершился с кодом `0`, выведено `Резервная копия создана: ...`, архив содержит `pgdump.bin`, `manifest.json` и при включённом Redis — `redis.rdb`. Манифест соответствует версии установки. После запуска `/readyz` возвращает `status: ready`. Если создание копии не удалось, не объявляйте её пригодной; определите стадию ошибки и отдельно примите решение о возобновлении записи.

## Проверка пригодности

1. На узле с достаточными ресурсами и доступными образами выполните:

   ```bash
   bash ops/backup/verify.sh /путь/к/redlycoris-архив.tar.gz
   ```

2. Проверьте весь вывод, в том числе восстановление PostgreSQL и количество записей. Сопоставьте его с контрольными данными установки, полученными при остановленной записи.

Проверка результата: код `0`, сообщение `Backup verification passed.`, успешный `pg_restore`, наличие таблиц `findings`, `projects`, `users`. Временный проект с уникальным именем удаляется обработчиком завершения; основные контейнеры не должны измениться.

Пределы этой проверки существенны. `backup.sh` не записывает `expected_counts`, поэтому `verify.sh` обычно сообщает, что строгое сравнение количества записей пропущено. Проверка Redis ограничена запуском, PING и выводом DBSIZE; контрольные ключи и содержимое очереди с исходным снимком не сравниваются. Кроме того, временный `/data` задан через `tmpfs`, а RDB копируется между остановкой и повторным стартом контейнера: успешный PING нельзя считать доказательством загрузки именно переданного снимка. Поведение такого хранилища описано в [справочнике Docker tmpfs](https://docs.docker.com/engine/storage/tmpfs/).
