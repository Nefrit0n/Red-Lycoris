# Разработка-Справочник-API

REST API использует JSON и маршруты `/api/v1`. Эта страница описывает общие правила контракта. Полный набор маршрутов, тел, параметров и ответов указан в [OpenAPI-спецификации](https://github.com/Nefrit0n/Red-Lycoris/blob/main/backend/api/openapi.yaml); не дублируйте её здесь.

## Интерактивная документация

Swagger UI и выдача OpenAPI зарегистрированы только при `ENV=dev`:

| Адрес | Назначение |
|---|---|
| `http://localhost:8080/api/docs` | Swagger UI |
| `http://localhost:8080/api/openapi.yaml` | Спецификация OpenAPI |

Проверьте результат: запустите сервер с `ENV=dev`, затем откройте `/api/docs`. В другом окружении эти маршруты не регистрируются и не должны использоваться как production-интерфейс документации.

## Аутентификация

Пользователь получает серверную сессию через `POST /api/v1/auth/login`. В браузере сервер устанавливает cookie `rl_session`; она `HttpOnly`, `SameSite=Lax`, а `Secure` зависит от `COOKIE_SECURE`. При отсутствии cookie сессионный токен допускается в `Authorization: Bearer <token>`.

Для CI используется проектный API-токен с префиксом `rl_pat_`. Маршрут `POST /api/v1/scans` требует PAT со scope `scans:write`; проект определяется токеном. Не передавайте токены в query-параметрах и не включайте их в логи.

Большинство рабочих маршрутов требует аутентификацию и не допускает пользователя, которому требуется сменить пароль. Проектные действия дополнительно проверяют роль. Статусы и границы ролей приведены в [модели безопасности](Система-Модель-безопасности).

Проверьте результат: запрос без действующей сессии или PAT к защищённому маршруту возвращает ошибку аутентификации; действующий PAT другого проекта не даёт доступ к скану этого проекта.

## Формат ответов

Списочные обработчики используют оболочку:

```json
{
  "data": [],
  "meta": {
    "total": 0,
    "next_cursor": "…",
    "has_more": false
  }
}
```

Ошибки используют:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "…",
    "request_id": "…"
  }
}
```

`request_id` позволяет сопоставить ответ с логом сервера. Не все успешные маршруты имеют одинаковую оболочку: например, публичный маршрут версии возвращает собственный объект. При разработке клиента ориентируйтесь на схему конкретного маршрута, а не на обобщённый пример.

Проверьте результат: для ошибочного запроса в теле есть `error.code`, `error.message` и `error.request_id`; для списка присутствуют `data` и `meta`.

## Курсорная пагинация

Списки передают `limit` и при наличии следующей страницы непрозрачный `cursor`. Клиент передаёт значение `meta.next_cursor` в следующий запрос и прекращает загрузку при `meta.has_more=false`. Не разбирайте и не создавайте курсор самостоятельно.

```text
GET /api/v1/findings?limit=50&cursor=<next_cursor>
```

Значение `limit` обработчики нормализуют по собственным правилам. Не рассчитывайте, что один и тот же максимум действует на каждом маршруте. Не используйте OFFSET как альтернативу курсору.

Проверьте результат: сохраните `next_cursor` первой страницы, передайте его следующему запросу и убедитесь, что `has_more` меняется только по ответу API.

## Ошибки и статусы

| HTTP-статус | Примеры кода | Значение для клиента |
|---|---|---|
| 400 | `BAD_REQUEST`, `VALIDATION_ERROR`, `PARSE_ERROR` | Исправьте тело, параметры или формат отчёта; повтор без изменения не решит ошибку |
| 401 | `UNAUTHORIZED`, `AUTHENTICATION_REQUIRED`, `FORCE_PASSWORD_CHANGE` | Обновите сессию/токен или смените пароль в предусмотренном потоке |
| 403 | `FORBIDDEN`, `INVALID_CURRENT_PASSWORD` | Проверьте роль, принадлежность проекта и данные текущего пароля |
| 404 | `NOT_FOUND` | Проверьте идентификатор и доступность ресурса |
| 409 | Зависит от обработчика | Проверьте конфликт состояния по контракту конкретного маршрута |
| 429 | `RATE_LIMITED` | Учитывайте заголовок `Retry-After`, если он присутствует, затем повторите позже |
| 500 | `INTERNAL_ERROR` | Сохраните `request_id` и обратитесь к журналу сервера; не раскрывайте пользователю внутреннюю ошибку |

Коды в таблице — категории, встречающиеся в обработчиках, а не закрытый enum контракта. Новая ветка обработчика может использовать другой код. Полный ответ и статус всегда проверяйте в OpenAPI и реализации выбранного коммита.

Проверьте результат: клиент обрабатывает HTTP-статус и `error.code` независимо; текст `message` не используется как машинный идентификатор.

## Расхождение спецификации и маршрутов

Спецификация является важным контрактом, но в текущем коде она не полностью совпадает с регистрацией маршрутов. В частности, `POST /api/v1/scans` зарегистрирован в router, но не описан в текущем `openapi.yaml`; альтернативный `POST /api/v1/findings`, описанный спецификацией, не зарегистрирован router. При изменении контракта обновляйте оба источника и проверяйте фактический маршрут.

Проверьте результат: для изменённого endpoint сопоставьте путь и middleware в `router.go` с записью в `openapi.yaml`, затем выполните запрос к запущенному серверу.
