# Разработка-Миграции

Схема PostgreSQL изменяется парными SQL-файлами golang-migrate в `backend/migrations`. Сервер применяет все неприменённые миграции при старте до открытия HTTP-порта. Ошибка миграции останавливает запуск сервера.

## Создание миграции

1. Сначала изучите актуальную схему и последние файлы миграций. Номер новой миграции должен быть следующим после наибольшего номера в каталоге; не ориентируйтесь на старые документы или количество файлов в тексте.

2. Создайте два файла с одинаковым номером и названием:

   ```text
   backend/migrations/NNN_краткое_название.up.sql
   backend/migrations/NNN_краткое_название.down.sql
   ```

3. В `up.sql` внесите прямое изменение. Используйте `snake_case`, UUID-ключи через `gen_random_uuid()`, `TIMESTAMPTZ` для времени и осмысленные имена индексов `idx_{table}_{columns}`. Учитывайте существующие индексы и фактические условия запросов.

4. В `down.sql` опишите технически возможный обратный путь. Не объявляйте откат безопасным, если прямое изменение удаляет данные, сужает тип, меняет семантику или вызывает необратимую backfill-операцию.

5. Если таблица партиционирована, предусмотрите жизненный цикл новых партиций. Статические границы SQL не создают будущие партиции сами. Особенности существующих `raw_findings`, `audit_log` и `epss_history` приведены в [схеме БД](Система-Схема-базы-данных).

Проверьте результат: оба файла существуют, имеют одинаковый номер и имя, а SQL проверен на чистой копии БД до использования рабочих данных.

## Применение локально

Запустите backend с подключением к целевой локальной БД:

```bash
cd backend
go run ./cmd/server
```

Сервер вызывает `m.Up()` с источником `file://migrations`. Успех или `ErrNoChange` позволяет продолжить запуск; другая ошибка завершает процесс. Цель Makefile `make migrate` запускает бинарный файл backend в уже работающем контейнере, поэтому не является отдельным CLI-инструментом выбора версии или отката.

Проверьте результат: лог сервера содержит `migrations applied`, сервер проходит `/readyz`, а ожидаемые объекты присутствуют в PostgreSQL. Для проверки схемы используйте SQL-инструмент, подключённый к той же БД, и не полагайтесь только на отсутствие ошибки запуска.

## Проверка до review

1. Поднимите чистую локальную БД и примените все миграции запуском сервера.
2. Выполните сценарий приложения, ради которого добавлена схема.
3. Проверьте нужные индексы и план целевого запроса на репрезентативном наборе данных.
4. Проверьте `down.sql` только на disposable БД и только если откат предусмотрен изменением.
5. Добавьте или обновите тесты кода, который читает новую схему.

Проверьте результат: чистая БД проходит путь `up`, приложение работает с новой схемой, а пробный `down` не затронул рабочую БД.

> **Предупреждение.** Не выполняйте `down.sql` на рабочей БД только ради проверки. Down-миграция может удалить таблицу, столбец или данные. Наличие файла `.down.sql` не означает без потерь выполняемый откат выпуска.

## Изменения данных и совместимость

Большие backfill-операции, изменения индексов и партиций могут удерживать блокировки или долго выполняться. Разделяйте изменение схемы, наполнение данных и переключение кода, когда это необходимо для эксплуатационного окна. Новая версия приложения должна явно учитывать, какой вариант схемы ей нужен.

Сервер автоматически применяет прямые миграции, но код не задаёт формальную матрицу допустимых переходов версий, совместной работы нескольких версий сервера или без потерь отката. Для обновления используйте копию данных и резервную копию; см. [обновление](Администратор-Обновление).
