# Администратор-Диагностика

Начните с наблюдения, не с удаления данных. Команды приведены для Bash на Linux из корня нужной установки. Используйте тот же набор Compose-файлов и имя проекта, что при запуске; для корневого production overlay можно задать `export COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml`.

Нельзя применять `make clean`, `down -v`, удалять Redis Stream или менять `schema_migrations` ради проверки гипотезы. Сначала сохраните журналы и сведения о версии без секретов.

## Быстрая локализация

| Симптом | Возможная причина по реализации | Направление решения |
| --- | --- | --- |
| Backend не открыл порт, миграции не применились | Соединение с PostgreSQL, каталог миграций, ошибка SQL или dirty-схема | Проверить журнал и `schema_migrations`; при изменённой схеме следовать процедуре обновления |
| `/readyz` возвращает `503` | Не проходит Ping PostgreSQL или Redis | Прочитать `checks` и проверить соответствующее хранилище |
| Backend/frontend помечены `unhealthy`, но интерфейс доступен | Ошибочные команды healthcheck поставки | Проверять фактические HTTP-маршруты, отдельно исправлять конфигурацию probe |
| Внешнее обогащение не запускается | Планировщик выключен либо не наступил первый тик | Проверить окружение, ручной запуск и статусы |
| Первая синхронизация OSV завершается ошибкой или длится долго | Сетевой таймаут, объём архива, место во временном каталоге, общая длительность | Разделить скачивание, разбор и запись по журналу экосистем |
| Вход возвращает `429 RATE_LIMITED` | Превышен счётчик пары адрес/почта | Проверить Retry-After, TTL и доверие прокси; дождаться окончания окна |
| Сообщения остались pending | Ошибка обогащения; повтор своих pending выполняется при старте worker | Устранить причину, проверить владельцев и только затем перезапускать backend |

## Не применились миграции

Симптом → backend перезапускается или HTTP-порт не открыт, в журнале есть `failed to init migrations` либо `failed to run migrations`.

Причина → миграции выполняются до HTTP-сервера и bootstrap. Образ содержит свой каталог миграций; новые файлы только в рабочей копии не обновляют уже собранный образ. Если источник миграций отсутствует или SQL завершается ошибкой, main выходит. Успешный выход старого контейнера или готовность PostgreSQL не подтверждают применение схемы приложения.

1. Снимите данные до вмешательства:

   ```bash
   docker compose ps -a
   docker compose logs --tail=200 backend
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version, dirty FROM schema_migrations;"'
   printf '%s\n' backend/migrations/*.up.sql | sort
   docker compose images
   ```

2. Сопоставьте образ, ревизию и номер миграции. При `dirty=t` остановите backend и перейдите к разделу ошибок [обновления](Администратор-Обновление). Если ошибка до миграций, исправьте соединение или состав образа; не запускайте `make migrate` внутри работающего backend.

Проверка результата: после устранения причины схема имеет ожидаемую версию и `dirty=f`, `/readyz` отвечает `200`. Неожиданно отсутствующая таблица `schema_migrations` требует проверки правильности выбранной БД, а не ручного создания этой таблицы.

## Readyz красный

Симптом → `/readyz` возвращает `503` либо проверка получает не JSON.

Причина → хранилище не прошло Ping за отведённое время или проверяется порт frontend вместо backend. `/readyz` при ошибке сообщает отдельные элементы `postgres` и `redis`; при успехе массив проверок не обязателен.

1. Получите тело ответа и проверьте зависимости:

   ```bash
   curl --silent --show-error -i http://localhost:8080/readyz
   docker compose exec -T postgres sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
   docker compose exec -T redis redis-cli PING
   docker compose logs --tail=100 postgres redis backend
   ```

2. Для ошибочного компонента сопоставьте состояние контейнера, адрес в конфигурации backend, доступность внутренней сети и журнал хранилища. Локальный `pg_isready` проверяет хранилище, но не правильность пароля в соединении backend. Если получен HTML, исправьте адрес проверки.

Проверка результата: `/readyz` возвращает `200` и `status: ready`; `/health` показывает `ok` для БД и Redis. Одного `PONG` или `healthy` контейнера недостаточно для проверки всего пути подключения.

## Контейнер unhealthy при доступном приложении

Симптом → Docker показывает ошибку backend или production frontend, прямые запросы работают.

Причина → backend проверяется командой `/app/admin --help`, отсутствующей в CLI; frontend проверяется по `8080`, хотя nginx слушает `3000`. Dockerfile backend содержит отдельный `/app/healthcheck`, но Compose переопределяет проверку.

1. Проверьте команды и результаты, не выводя полную конфигурацию с секретами:

   ```bash
   docker inspect redlycoris-backend --format '{{json .Config.Healthcheck}} {{json .State.Health}}'
   docker inspect redlycoris-frontend --format '{{json .Config.Healthcheck}} {{json .State.Health}}'
   curl --fail --silent --show-error http://localhost:8080/readyz
   curl --fail --silent --show-error http://localhost:3000/api/v1/version
   ```

2. Исправьте probe в согласованной конфигурации: backend может использовать включённый `/app/healthcheck`, который проверяет только `/healthz`; для frontend проверяйте реальный порт и наличие утилиты в образе. Пересоздание контейнеров согласуйте отдельно.

Проверка результата: реальные HTTP-запросы успешны; после исправления probe её команда существует, обращается к нужному порту и возвращает код `0`. Проверка живости backend не заменяет `/readyz`.

## Обогащение не идёт

Симптом → после запуска нет свежих баз, ручной запрос не приводит к завершению или находка не меняется.

Причина → внешние синхронизации и обогащение находок из локальной БД — разные процессы. При `ENRICHMENT_ENABLED=false` синхронизаторы не регистрируются, но очередь работает. При `true` планировщик не запускает синхронизацию немедленно: первый запуск происходит по интервалу или вручную. Отсутствие совпадающих идентификаторов в локальных базах также не является сбоем очереди.

1. Проверьте окружение и состояние:

   ```bash
   docker inspect redlycoris-backend --format '{{range .Config.Env}}{{println .}}{{end}}' | grep '^ENRICHMENT_ENABLED='
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT source, status, last_sync_at, records_count, error_message, duration_seconds FROM sync_status ORDER BY source;"'
   docker compose exec -T redis redis-cli XINFO GROUPS enrichment:pending
   docker compose logs --since=30m backend
   ```

2. Если внешняя синхронизация разрешена, под администратором запустите нужный источник. Пример в консоли браузера приложения:

   ```javascript
   await fetch('/api/v1/enrichment/sync/osv', { method: 'POST' })
     .then(async r => ({ status: r.status, body: await r.json() }))
   ```

   Не запускайте источник повторно, пока выясняете состояние предыдущего запуска. Ответ `202` выдаётся до выполнения фоновой задачи; при уже работающей синхронизации новая попытка может быть отклонена только внутри планировщика и отражена в журнале.

3. При сетевой ошибке проверьте [разрешённые адреса и особенности прокси](Администратор-Работа-в-закрытом-контуре). Для NVD наличие `HTTPS_PROXY` не означает его использования; для БДУ не устраняйте TLS-ошибку отключением проверки сертификата.

Проверка результата: выбранный источник завершился, статусы и журнал не содержат соответствующей ошибки, локальные данные актуализированы. Для находок дополнительно проверьте успешную обработку очереди и карточку контрольной находки. Команда `make sync` не передаёт аутентификацию; её выполнение не является подтверждением запуска административных маршрутов.

## Таймаут первой синхронизации OSV

Симптом → длительное скачивание, `context deadline exceeded`, ошибка отдельной экосистемы либо общий success при неполном наполнении.

Причина → OSV последовательно обрабатывает список экосистем. HTTP-клиент имеет таймаут 30 минут на запрос, а планировщик ограничивает запуск четырьмя часами. Архив загружается во временный файл, затем разбирается и записывается пакетами. Таймаут HTTP-сервера API не равен времени фоновой синхронизации.

1. Найдите последнюю успешную стадию и экосистему:

   ```bash
   docker compose logs --since=4h --no-color --no-log-prefix backend | grep -E 'OSV sync|scheduler: sync|sync failed|manual sync failed'
   docker stats --no-stream redlycoris-backend redlycoris-postgres
   docker compose exec -T postgres df -h /var/lib/postgresql/data
   docker system df
   ```

   На уровне `warn` подробности скачивания и прогресса скрыты. При необходимости временно включите INFO через локальный overlay; пересоздание backend прервёт текущую задачу. Дополнительно проверьте свободное место на файловой системе Docker, где находится writable-слой backend и временный файл OSV.

2. Сопоставьте сообщения `downloading ecosystem`, `downloaded ecosystem archive`, `archive opened`, `progress`, `ecosystem failed`. Устраните сетевую ошибку, нехватку места или ограничение ресурсов до повторного запуска.
3. После завершения или остановки предыдущей задачи повторите разрешённый ручной запуск. Переменной окружения для изменения таймаута OSV или выбора экосистем нет; не задавайте выдуманные `OSV_TIMEOUT` или `OSV_ECOSYSTEMS`.

Проверка результата: в журнале виден прогресс и завершение нужных экосистем, нет повторяющихся ошибок, локальные данные присутствуют. Синхронизатор продолжает цикл после ошибок отдельных экосистем и может вернуть общий успех, поэтому одного `sync_status.status=success` недостаточно.

## 429 при входе

Симптом → `POST /api/v1/auth/login` возвращает HTTP `429`, код `RATE_LIMITED`.

Причина → счётчик Redis имеет ключ `ratelimit:login:<IP>:<почта>`. Почта приводится к нижнему регистру, пробелы по краям удаляются. Счётчик увеличивается перед аутентификацией, при первом запросе получает TTL 15 минут; запрос с количеством больше 5 отклоняется. Успешный вход удаляет ключ. При ошибке Redis INCR ограничение пропускается, поэтому отсутствие `429` не доказывает исправность защиты.

1. В сетевой панели браузера посмотрите тело ответа и `Retry-After`; не повторяйте вход циклически.
2. Для установленной пары IP/почта проверьте только её ключ, заменив пример реальными значениями:

   ```bash
   docker compose exec -T redis redis-cli GET 'ratelimit:login:192.0.2.10:user@example.org'
   docker compose exec -T redis redis-cli TTL 'ratelimit:login:192.0.2.10:user@example.org'
   ```

3. Дождитесь истечения указанного окна и повторите вход с правильными данными. Если адрес общий для пользователей за прокси либо подменяемый, исправьте [границу доверия](Администратор-Безопасная-сетевая-конфигурация). Не меняйте IP и не удаляйте ключи как штатный способ обхода ограничения.

Проверка результата: после окончания окна правильный вход возвращает `200`, соответствующий ключ удаляется успешным обработчиком. Значение TTL `-2` означает отсутствие ключа; `-1` — отсутствие срока истечения и требует отдельной диагностики, а не бесконечного ожидания. Значения ответа приведены по [справочнику Redis TTL](https://redis.io/docs/latest/commands/ttl/).

## Зависшие сообщения Redis Stream

Симптом → pending не уменьшается, находки не получают данные, хотя общая метрика lag равна нулю.

Причина → очередь называется `enrichment:pending`, группа — `enrichment-workers`. Обработчик подтверждает сообщение только после успешного обогащения; при ошибке оставляет его pending. Неверный формат сообщения или UUID подтверждается и пропускается. XACK не удаляет сообщение из самого Stream, поэтому XLEN не является числом необработанных заданий.

1. Проверьте общую очередь и владельцев сообщений:

   ```bash
   docker compose exec -T redis redis-cli XINFO GROUPS enrichment:pending
   docker compose exec -T redis redis-cli XINFO CONSUMERS enrichment:pending enrichment-workers
   docker compose exec -T redis redis-cli XPENDING enrichment:pending enrichment-workers
   docker compose exec -T redis redis-cli XPENDING enrichment:pending enrichment-workers - + 10
   docker compose logs --since=30m backend | grep -E 'enrichment worker|consumer group'
   ```

2. Устраните конкретную ошибку PostgreSQL или обогащения. Для штатных имён `worker-0`, `worker-1`, `worker-2` собственные pending читаются при старте worker. После устранения причины перезапустите backend в согласованное окно:

   ```bash
   docker compose restart backend
   curl --fail --silent --show-error http://localhost:8080/readyz
   docker compose exec -T redis redis-cli XPENDING enrichment:pending enrichment-workers
   ```

   Перезапуск прерывает API и синхронизации. Не выполняйте его до устранения причины: цикл начального чтения pending не имеет отдельного backoff на ошибку обогащения и может повторять неуспешное сообщение.

3. Если pending принадлежат другому consumer, не рассчитывайте на автоматический захват: XCLAIM/XAUTOCLAIM в worker не реализованы. Сохраните идентификаторы и согласуйте отдельный план восстановления владельца сообщений.

Проверка результата: `/readyz` готов, число pending у штатных обработчиков уменьшается, сообщения `enrich failed` не повторяются, контрольные находки обработаны. Отсутствие pending не означает нулевой XLEN. Не используйте XACK, XDEL, DEL или FLUSHALL для «лечения» очереди: они могут скрыть или уничтожить задания.
