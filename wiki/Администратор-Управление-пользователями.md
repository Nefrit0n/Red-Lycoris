# Администратор-Управление-пользователями

Начальное создание пользователей описано в [первичной настройке](Администратор-Первичная-настройка). Здесь приведены действующие проверки доступа и эксплуатационные ограничения. Название роли в интерфейсе и наличие записи в таблице разрешений сами по себе не доказывают применение этих разрешений API.

## Роли и права

Глобальная проверка использует `users.global_role`: `0` — обычный пользователь, `1` — администратор. Проектные проверки используют `user_project_roles`, где роли сравниваются по числовому уровню.

| Операция | Минимальное право для сессионного пользователя |
| --- | --- |
| Чтение проекта, находок, обогащений, истории и сканирований | Наблюдатель проекта (`viewer`, `0`) |
| Триаж, назначение ответственного, создание комментария, запуск обогащения находки, `/api/v1/import` | Триаж (`triager`, `1`) |
| Изменение проекта, управление участниками и создание/отзыв API-токенов | Администратор проекта (`project_admin`, `2`) |
| Удаление отдельной находки | Администратор проекта |
| Удаление проекта | Владелец проекта или глобальный администратор; одной роли администратора проекта недостаточно |
| Создание проекта | Аутентифицированный пользователь после обязательной смены пароля; создатель получает роль администратора проекта |
| Управление пользователями, административный аудит, внешняя синхронизация, `enrich-all` | Глобальный администратор |

Глобальный администратор обходит проверки минимальной проектной роли и владельца проекта. Таблица относится к сессиям: API-токены имеют отдельный путь проверки и scopes, а `/api/v1/scans` требует именно API-токен. Не переносите права сессионных ролей на токены по аналогии.

Форма создания принимает `admin`, `auditor`, `member`, `viewer`. Только `admin` устанавливает `global_role=1`; остальные варианты дают `0`. Таблицы `roles`, `permissions`, `role_permissions`, `user_roles` существуют, а миграция `028` синхронизирует признак администратора с `user_roles`. Однако middleware не рассчитывает доступ по `role_permissions`. Поэтому «Аудитор» в форме не получает административный аудит автоматически, а глобальное имя «Наблюдатель» не заменяет проектную роль чтения.

### Проверка назначений

1. В браузере администратора откройте пользователя и проект. Для чтения назначений выполните, заменив идентификаторы:

   ```javascript
   await fetch('/api/v1/admin/users/<идентификатор>/roles').then(r => r.json())
   await fetch('/api/v1/projects/<идентификатор>/members').then(r => r.json())
   ```

2. В отдельной сессии целевого пользователя проверьте доступ к проекту:

   ```javascript
   await fetch('/api/v1/projects/<идентификатор>').then(r => r.status)
   ```

Проверка результата: административные запросы показывают нужное назначение; целевой пользователь получает HTTP `200` для разрешённого проекта. При отсутствии проектной роли ожидается `403` с `INSUFFICIENT_PROJECT_ROLE`. Проверяйте фактическое действие, а не только подпись роли.

## Группы и project_access

| Сущность | Реализация и ограничение |
| --- | --- |
| `groups` | Список групп, уникальность имени без учёта регистра после миграции `028`; значения `source`: `manual`, `ldap_sync` |
| `user_groups` | Членство; существующие группы можно назначить при создании пользователя |
| `project_access` | `subject_kind`: `user` или `group`; `access_level`: `read`, `write`, `admin`; триггер проверяет существование субъекта |
| `user_project_roles` | Действующее хранилище для проверок проектной роли и API участников |

Миграция `026` однократно переносит назначения из `user_project_roles` в `project_access`. Последующие операции `Grant`, `Update`, `Revoke` изменяют `user_project_roles`, а проверки `GetRole` читают её же. Наличие `project_access` не означает, что группа предоставляет доступ к проекту. Штатных маршрутов создания групп и управления `project_access` в текущем router нет. Значение `ldap_sync` в схеме не подтверждает работающую LDAP-синхронизацию.

Не вносите прямые SQL-назначения в `project_access` как замену штатному управлению участниками. Команда проекта (`teams`) также не является группой доступа.

## Деактивация вместо удаления

Для прекращения доступа используйте деактивацию. `POST /api/v1/admin/users/{id}/deactivate` устанавливает `is_active=false`, `status=disabled`, отзывает сессии и записывает административное событие. Причина должна содержать не менее 10 символов после удаления краевых пробелов.

Маршрут `DELETE /api/v1/admin/users/{id}` также выполняет мягкое отключение, а не физическое удаление. Несмотря на комментарий в коде, обработчик не обезличивает имя и адрес. Кроме того, проверка последнего администратора применяется к деактивации и снятию роли, но не к действию `ActionDelete`. Не используйте DELETE как эквивалент защищённой деактивации.

### Отключение учётной записи

Предупреждение: операция прекращает пользовательские сессии. Убедитесь, что отключаете нужную учётную запись и что имеется другой действующий администратор. Отключение пользователя не является процедурой отзыва всех проектных API-токенов: проверьте их отдельно.

1. Под другим администратором найдите пользователя по адресу в списке `/admin/access/users` и сопоставьте идентификатор.
2. Вызовите деактивацию через интерфейс либо в консоли браузера администратора:

   ```javascript
   await fetch('/api/v1/admin/users/<идентификатор>/deactivate', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({ reason: 'Доступ прекращён по согласованной заявке' })
   }).then(async r => ({ status: r.status, body: await r.json() }))
   ```

3. Проверьте состояние в списке пользователей:

   ```javascript
   await fetch('/api/v1/admin/users?q=' + encodeURIComponent('user@example.org'))
     .then(async r => ({ status: r.status, body: await r.json() }))
   ```

Проверка результата: операция возвращает HTTP `200`, `data.status: deactivated`, в списке — отключённое состояние. В прежней сессии пользователя запрос `/api/v1/auth/me` больше не должен возвращать действующую учётную запись; новый вход также отклоняется. Если после изменения БД отзыв сессий завершился ошибкой, обработчик может вернуть `500`: проверьте состояние, прежде чем повторять действие.

| Защита API | Код ответа |
| --- | --- |
| Отключение собственной записи, сброс собственного пароля административным действием, снятие собственной роли администратора | `403 SELF_MODIFICATION_FORBIDDEN` |
| Отключение системного аккаунта или снятие его роли администратора | `403 SYSTEM_ACCOUNT_PROTECTED` |
| Отключение последнего активного администратора или снятие его роли | `403 LAST_ADMIN_PROTECTED` |

Подсчёт активных администраторов использует `global_role=1 AND status='active'`, тогда как проверка действующей сессии использует `is_active`. Эти признаки могут разойтись после CLI-операций или при статусе `pending`. Перед изменением административного доступа проверяйте оба поля и наличие реально работающей второй учётной записи; не считайте проверку счётчика полной защитой от потери доступа.

### Повторное включение

1. Убедитесь, что доступ пользователю разрешён повторно. Вызовите `POST /api/v1/admin/users/{id}/activate` с JSON-полем `reason` из административной сессии.
2. Повторите читающий запрос списка пользователей из предыдущей процедуры и попросите пользователя выполнить новый вход.

Проверка результата: HTTP `200`, `data.status: activated`; запись имеет `is_active=true`, `status=active`. Ранее отозванные сессии не восстанавливаются. Если операция запрещена для системного аккаунта, API возвращает `403 SYSTEM_ACCOUNT_PROTECTED`.

## CLI /app/admin

CLI подключается непосредственно к PostgreSQL через `DATABASE_URL`, до разбора команды. Он не применяет миграции и не вызывает HTTP API. Доступ к контейнеру с CLI следует считать административным доступом к БД.

| Команда | Параметры | Реальное действие |
| --- | --- | --- |
| `list-users` | Нет | Печатает общее число и до 200 пользователей; параметров пагинации нет |
| `create-user` | Обязательные `--email`, `--password`; необязательные `--admin`, `--full-name` | Создаёт активную запись; `--admin` по умолчанию выключен; не устанавливает обязательную смену пароля |
| `reset-password` | Обязательные `--email`, `--password` | Заменяет хеш; не отзывает сессии и не устанавливает обязательную смену |
| `deactivate` | Обязательный `--email` | Меняет `is_active`; не выполняет API-проверки последнего администратора и системного аккаунта, не обновляет `status` и не отзывает записи сессий |

CLI не реализует отдельный безопасный ввод пароля из stdin: аргумент `--password` может быть виден в списке процессов и журнале оболочки. Для штатных операций используйте интерфейс/API. В CLI отсутствует верхнеуровневая команда `--help`; именно поэтому проверка backend из базового Compose неверна.

### Проверка CLI без изменения данных

1. На узле установки выполните:

   ```bash
   docker compose exec -T backend /app/admin list-users
   ```

2. Для production добавьте к Compose те же файлы `-f`, что при запуске.

Проверка результата: вывод начинается с `total users:` и содержит адреса, признаки `active`, числовые роли и время последнего входа. Отсутствие пользователя среди первых 200 строк не доказывает отсутствие записи. Ошибка соединения требует проверки БД, а не повторного создания пользователя.
