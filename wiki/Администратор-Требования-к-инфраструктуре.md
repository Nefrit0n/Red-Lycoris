# Администратор-Требования-к-инфраструктуре

Страница описывает ограничения поставляемой конфигурации Docker Compose. Лимиты контейнеров не являются результатами нагрузочных испытаний и не определяют вместимость установки.

## Ресурсные профили

| Профиль | CPU | Оперативная память | Диск |
| --- | --- | --- | --- |
| Ознакомительный | Минимум не установлен | Минимум не установлен | Минимум не установлен |
| До 100k находок | Требуется измерение на целевой нагрузке | Требуется измерение на целевой нагрузке | Требуется измерение объёма данных и темпа роста |
| 1M+ находок | Требуется измерение на целевой нагрузке | Требуется измерение на целевой нагрузке | Требуется измерение объёма данных и темпа роста |

<!-- TODO: уточнить --> Для трёх профилей отсутствуют подтверждённые кодом нормативы CPU, RAM и диска. Не используйте значения из старой документации как гарантированную конфигурацию.

На размер установки влияют не только находки, но и исходные результаты импорта, индексы, история изменений, локальные данные обогащения и резервные копии. Планируйте отдельный запас для сборки образов и обслуживания БД; числовой коэффициент запаса в поставке не задан.

### Заданные ограничения контейнеров

Значения ниже непосредственно заданы в `deploy.resources`. Они ограничивают контейнеры; резервирование памяти и ограничение её потребления — разные параметры.

| Сервис | Базовый файл: предел CPU / памяти | Базовый файл: резерв памяти | С production overlay: предел CPU / памяти | С production overlay: резерв памяти |
| --- | --- | --- | --- | --- |
| PostgreSQL | `1.0` / `1G` | `512M` | `2.0` / `2G` | `1G` |
| Redis | `0.5` / `512M` | `128M` | `1.0` / `512M` | `256M` |
| Backend | `1.0` / `512M` | `128M` | `2.0` / `1G` | `256M` |
| Frontend | `0.5` / `512M` | `128M` | `0.5` / `512M` | `128M` |

Эти настройки не учитывают потребление ОС и сборщика. Production overlay изменяет лимиты PostgreSQL, но не меняет его параметры `shared_buffers`, `work_mem` и `max_connections` из базового файла.

## ОС и контейнерная среда

| Компонент | Подтверждённое состояние |
| --- | --- |
| Серверное приложение | В Dockerfile для основного серверного бинарного файла задана сборка `GOOS=linux GOARCH=amd64` |
| ОС узла | Матрица поддерживаемых дистрибутивов и версий не задана |
| Astra Linux, РЕД ОС | Поддержка и результаты испытаний не подтверждены кодом поставки |
| Docker Engine | Числовой минимум не закреплён; необходима работа Linux-контейнеров и сборок из Dockerfile |
| Compose | Используется команда `docker compose`; production overlay требует обработки тега `!reset` |
| PostgreSQL / Redis | Поставляются образы `postgres:16-alpine` и `redis:7-alpine` |

### Проверка узла перед установкой

1. Выполните команды на целевом узле:

   ```bash
   uname -srm
   docker version
   docker compose version
   docker info --format '{{.OSType}} {{.Architecture}}'
   ```

2. После подготовки `.env` проверьте оба файла вместе из корня репозитория:

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml config --quiet
   ```

Проверка результата: `docker version` должен показать клиент и доступный сервер; `docker info` — тип `linux` и архитектуру, соответствующую сборке `amd64` (`x86_64`). Проверка Compose должна завершиться с кодом `0`, без ошибок `!reset` и обязательных переменных. Порядок подготовки `.env` приведён в [установке](Администратор-Установка-Docker-Compose).

## Дисковая подсистема PostgreSQL

Данные размещаются в именованном томе `redlycoris-pgdata`, подключённом к `/var/lib/postgresql/data`; драйвер тома — `local`. Отдельный том для WAL в поставке не задан. Redis использует отдельный том `redlycoris-redisdata` и AOF с `appendfsync everysec`.

| Параметр PostgreSQL | Значение в Compose | Значение для планирования |
| --- | --- | --- |
| `POSTGRES_INITDB_ARGS` | `--data-checksums` | Задано для инициализации нового кластера, не для переинициализации существующего тома |
| `random_page_cost` | `1.1` | Оценка стоимости в планировщике; не подтверждение типа или скорости накопителя |
| `effective_io_concurrency` | `200` | Настройка PostgreSQL, не гарантированное число IOPS |
| `max_wal_size` | `1GB` | Параметр WAL; не лимит размера всего тома |
| `checkpoint_completion_target` | `0.9` | Задано в команде запуска PostgreSQL |

<!-- TODO: уточнить --> Не установлены минимальные IOPS, задержки, объём, допустимые файловые системы и требования к отказоустойчивости дискового массива для профилей нагрузки.

Не выводите требование «достаточно SSD определённого объёма» из настроек планировщика. При выборе хранилища учитывайте требования PostgreSQL к сохранности подтверждённых записей; справочник компонента: [надёжность WAL](https://www.postgresql.org/docs/16/wal-reliability.html). Поставляемый Compose не настраивает контроллер, дисковый кэш или защиту питания.

### Проверка размещения данных после запуска

1. Найдите фактическое размещение томов:

   ```bash
   docker inspect redlycoris-postgres --format '{{json .Mounts}}'
   docker inspect redlycoris-redis --format '{{json .Mounts}}'
   ```

2. Проверьте доступное пространство и размер БД:

   ```bash
   docker compose exec -T postgres df -h /var/lib/postgresql/data
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT pg_size_pretty(pg_database_size(current_database())) AS database_size;"'
   ```

Проверка результата: в списке подключений должны присутствовать тома с указанными путями назначения, `df` должен показывать выбранное хранилище и свободное место, SQL — размер БД без ошибки подключения. Для production используйте те же два флага `-f`, что при запуске. Оцените запас по фактическому росту, а не только по текущему числу находок.
