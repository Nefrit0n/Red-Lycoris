# Администратор-Мониторинг-и-логи

Backend предоставляет проверки состояния и метрики на своём HTTP-порту. Штатный nginx frontend проксирует только `/api/`: запрос `/readyz` или `/metrics` через frontend может вернуть HTML приложения вместо нужного ответа. Используйте внутренний адрес backend и ограничьте доступ к служебным маршрутам.

## Проверки состояния

| Маршрут | Успех | Ошибка и ограничения |
| --- | --- | --- |
| `GET /healthz` | HTTP `200`, текст `ok` | Проверяет доступность обработчика, но не PostgreSQL и Redis |
| `GET /readyz` | HTTP `200`, JSON `status: ready` | При ошибке PostgreSQL или Redis — `503`, `status: not_ready`, массив `checks` с `name`, `ok`, `error` |
| `GET /health` | HTTP `200`, JSON со `status`, `version`, `uptime_seconds`, `components` | Проверяет SQL, Redis и чтение `sync_status`; при ошибке — `503`. Ошибка отдельного источника в строке `sync_status` сама по себе не меняет общий статус на error |
| `GET /api/v1/version` | HTTP `200`, `version`, `commit`, `build_date`, `go_version` | Метаданные сборки, не проверка готовности |
| `GET /metrics` | HTTP `200`, текст Prometheus | Показатели процесса; не проверка доступности всех внешних источников |

У `/readyz` отдельный таймаут 2 секунды для проверки каждого хранилища. Маршруты зарегистрированы без обязательной аутентификации, поэтому защитите их сетевыми правилами. Публичный прокси не должен раскрывать ошибки соединения с БД.

### Проверка доступности

1. Выполните с узла мониторинга, заменив адрес и порт при необходимости:

   ```bash
   curl --fail --silent --show-error http://localhost:8080/healthz
   curl --fail --silent --show-error http://localhost:8080/readyz
   curl --fail --silent --show-error http://localhost:8080/health
   curl --fail --silent --show-error http://localhost:8080/api/v1/version
   ```

2. Если `/readyz` отвечает ошибкой, повторите запрос без `--fail`, чтобы увидеть диагностическое тело:

   ```bash
   curl --silent --show-error -i http://localhost:8080/readyz
   ```

Проверка результата: при исправной установке получены указанные в таблице статусы, в `/health` у `components.database` и `components.redis` значение `status: ok`. HTML, ответ не с того порта или один успешный `/healthz` не подтверждают готовность хранилищ.

## Метрики

Метрики реализованы собственным реестром в `internal/observability/metrics.go`, а не стандартным набором Go-exporter. Не ожидайте автоматически доступных семейств `go_*` и `process_*`.

| Семейство | Тип | Метки | Смысл и область |
| --- | --- | --- | --- |
| `redlycoris_http_requests_total` | Счётчик | `route`, `method`, `status` | Обработанные HTTP-запросы; `route` — шаблон маршрута Chi либо `unknown` |
| `redlycoris_http_request_duration_seconds` | Гистограмма | `route`, `method` | Длительность HTTP-запросов в секундах |
| `redlycoris_enrichment_stream_lag` | Измеряемое значение | `source` | Lag группы Redis Stream; текущий сборщик публикует только `source=nvd` |
| `redlycoris_enrichment_last_sync_age_seconds` | Измеряемое значение | `source` | Возраст `last_sync_at` из `sync_status`; текущий сборщик читает только NVD |
| `redlycoris_import_findings_total` | Счётчик | `format`, `outcome`, `kind` | Обработанные записи пути `/api/v1/import`; исходы `inserted`, `updated`, `rejected`. В обработчике `/api/v1/scans` этот счётчик не обновляется |
| `redlycoris_db_pool_connections` | Измеряемое значение | `state` | Соединения pgxpool: `acquired`, `idle`, `total` |
| `redlycoris_build_info` | Измеряемое значение | `version`, `commit`, `date` | Константа `1` с метаданными сборки |

Гистограмма экспортирует суффиксы `_bucket`, `_sum`, `_count`; у bucket добавляется метка `le`. Границы в секундах: `0.005`, `0.01`, `0.025`, `0.05`, `0.1`, `0.25`, `0.5`, `1`, `2.5`, `5`, `10`, `+Inf`.

Пул опрашивается при запуске сборщика и затем каждые 15 секунд. Метрики обогащения обновляются при запуске и затем каждые 30 секунд. Счётчики и гистограммы живут в памяти процесса и сбрасываются после перезапуска; ряд может отсутствовать до первого наблюдения.

### Ограничения интерпретации

`redlycoris_enrichment_stream_lag` относится к общей очереди `enrichment:pending`, хотя метка называется `source=nvd`. Он не показывает число уже доставленных, но не подтверждённых сообщений. Для них используйте XPENDING. Если XINFO недоступен, код использует разность длины очереди и длины при старте, ограниченную снизу нулём; это не точный универсальный показатель задолженности.

`last_sync_age_seconds=0` может означать отсутствие строки, отсутствие времени или ошибку чтения, а не свежую синхронизацию. В `sync_status` `last_sync_at` также используется как служебная отметка синхронизатора, поэтому проверяйте вместе `status` и `error_message`. Метрики NVD не заменяют статусы EPSS, KEV, БДУ, CWE, CPE и OSV.

### Проверка сбора

1. Выполните контрольный запрос и получите метрики:

   ```bash
   curl --fail --silent --show-error http://localhost:8080/healthz
   curl --fail --silent --show-error http://localhost:8080/metrics
   ```

2. Настройте внутреннюю систему мониторинга на `/metrics` backend. Пороговые значения и интервалы опроса выберите по нагрузке и регламенту: готовые правила оповещения не задаются реестром приложения.

Проверка результата: ответ имеет тип `text/plain; version=0.0.4`, содержит строки `# HELP`, `# TYPE`, `redlycoris_build_info` со значением `1` и ряд запросов `/healthz`. Значения пула появляются после запуска сборщика; отсутствие ряда импорта до импорта допустимо.

## JSON-логи backend

Сервер создаёт `slog.NewJSONHandler(os.Stdout, ...)` для всех режимов ENV. Базовые поля — `time`, `level`, `msg`; дополнительные поля определяются местом записи. Запросы журналируются на INFO с `request_id`, `method`, `path`, `status`, `duration_ms`. Ошибки восстановления после panic включают `stack`.

| LOG_LEVEL | Поведение |
| --- | --- |
| `debug` | DEBUG и более высокие уровни |
| `info` или неизвестная строка | INFO и более высокие уровни |
| `warn` | WARN и ERROR; обычные сообщения запросов и прогресса синхронизации скрыты |
| `error` | ERROR |

Корневой production overlay задаёт `LOG_LEVEL: warn` буквально. Изменение `LOG_LEVEL` только в `.env` не переопределяет его. Для временной диагностики задайте уровень в локальном overlay и пересоздайте backend в согласованное окно; после работ верните штатный уровень. Пересоздание прерывает текущие задачи.

Логи остальных контейнеров и служебных Bash-скриптов не обязаны иметь формат JSON. Не обещайте единого формата всей команды `docker compose logs`. Не публикуйте журналы без проверки на чувствительные данные и внутренние адреса.

### Чтение логов

1. Используйте тот же набор Compose-файлов, что при запуске:

   ```bash
   docker compose logs --since=15m --tail=200 --no-color --no-log-prefix backend
   docker compose logs --since=15m --tail=100 postgres redis frontend
   ```

2. Сопоставьте время, `request_id` и сообщение с ошибкой API. Для синхронизации дополнительно сопоставьте `source`; для очереди — `consumer`, `msg_id`, `finding_id`.

Проверка результата: сообщения относятся к нужной установке и периоду; на INFO видны завершённые HTTP-запросы, на WARN их отсутствие ожидаемо. Отсутствие записи о синхронизации на WARN не доказывает, что задача не запускалась.

## Ротация контейнерных журналов

| Сервис | Драйвер | `max-size` | `max-file` |
| --- | --- | --- | --- |
| Backend | `json-file` | `20m` | `5` |
| PostgreSQL | `json-file` | `10m` | `3` |
| Redis | `json-file` | `10m` | `3` |
| Frontend | `json-file` | `10m` | `3` |

Это настройки Docker-журналов из базового Compose; корневой production overlay их не меняет. Они не являются сроком хранения аудита в PostgreSQL и не создают централизованный архив логов.

### Проверка ротации

1. Прочитайте фактическую конфигурацию контейнеров:

   ```bash
   docker inspect redlycoris-backend --format '{{json .HostConfig.LogConfig}}'
   docker inspect redlycoris-postgres --format '{{json .HostConfig.LogConfig}}'
   docker inspect redlycoris-redis --format '{{json .HostConfig.LogConfig}}'
   docker inspect redlycoris-frontend --format '{{json .HostConfig.LogConfig}}'
   ```

Проверка результата: драйвер и параметры совпадают с таблицей или с утверждённым локальным переопределением. Изменение Compose без пересоздания контейнера не является подтверждением применения новых параметров журналирования.

## Контейнерные healthcheck

Не подменяйте проверки HTTP статусом Docker `healthy`. Базовый Compose проверяет backend через неподдерживаемую команду `/app/admin --help`; production Dockerfile frontend проверяет `8080`, хотя nginx слушает `3000`. Эти расхождения описаны в [установке](Администратор-Установка-Docker-Compose); до исправления используйте прямые проверки и [диагностику](Администратор-Диагностика).
