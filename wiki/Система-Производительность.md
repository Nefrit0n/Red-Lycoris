# Система-Производительность

В реализации используются курсоры, индексы, локальные справочники, асинхронная обработка и виртуализация строк. Эти механизмы уменьшают отдельные составляющие нагрузки, но не являются подтверждением конкретной пропускной способности или времени ответа на миллионе находок. Значения зависят от распределения данных, запросов и ресурсов развёртывания.

## Чтение находок

### Курсорная пагинация

`FindingsRepo.List` кодирует в курсор `first_seen` и `id`. Для следующей страницы при убывающем порядке используется условие:

```sql
(f.first_seen, f.id) < ($1, $2)
```

При возрастающем порядке оператор меняется на `>`. UUID разрешает совпадения времени. При сортировке по `first_seen` такой подход позволяет продолжить чтение от последнего ключа без пропуска всех предыдущих строк через OFFSET. В миграциях есть соответствующие индексы `(first_seen DESC, id DESC)` и `(project_id, first_seen DESC, id DESC)`.

У текущей реализации есть существенная граница: условие курсора всегда построено по `first_seen`, хотя `ORDER BY` разрешает также `last_seen`, `severity` и `priority_score`. Для этих сортировок ключ курсора не соответствует порядку выдачи; при переходе между страницами возможны пропуски и повторы. Корректность полного обхода нельзя обосновывать наличием параметра `cursor` без учёта выбранной сортировки.

Каждый вызов списка отдельно выполняет `COUNT(*)` по полному набору фильтров, без ограничения курсором. Поэтому курсор сокращает работу получения страницы, но не отменяет стоимость подсчёта общего количества. Если возвращено ровно `limit` строк, сервер выдаёт следующий курсор без дополнительной проверки `limit + 1`; следующая страница может оказаться пустой.

### Состав выборки и фильтры

Список соединяет находки с оценками, проектами и назначенными пользователями. Его набор колонок включает основные поля находки, в том числе описание, `code_snippet`, `code_flow` и `http_evidence`: это не облегчённая проекция только видимых столбцов интерфейса. Полные снимки обогащения запрашиваются отдельно, но сводные признаки KEV/БДУ и максимумы EPSS/CVSS вычисляются коррелированными подзапросами к справочникам для строк списка. Объём ответа зависит и от размера текстовых/JSONB-полей, не только от `limit`.

| Механизм | Что даёт | Ограничение |
|---|---|---|
| B-tree по времени и проекту | Поддержка хронологической страницы и ограничения проекта | Не универсальный индекс для любой сортировки |
| GIN массива CVE | Поиск вхождения CVE через `@>` | Не распространяется автоматически на другие массивы; GIN `findings.cwe_ids` не создан |
| GIN полнотекстового вектора | Поиск по названию, описанию и компоненту без внешнего поискового сервиса | Конфигурация вектора и запроса — `english`, не русская морфология |
| Частичные индексы | Меньший индекс для открытых critical, назначенных открытых и других подмножеств | Помогают только подходящим предикатам |
| Составные kind/status/project | Поддержка сочетаний категории, статуса и проекта | Селективность зависит от данных |
| Индекс priority | Доступ к оценкам по приоритету | Оценка находится в отдельной таблице; остальные фильтры требуют соединения |

Групповой режим списка использует отдельный агрегирующий запрос с `GROUP BY`, сортировкой агрегатов и `LIMIT`. Это не тот же хронологический курсор. В интерфейсе группы загружаются через `useQuery`, а плоский список — через `useInfiniteQuery`. Наличие группировки не означает потоковый обход всех групп.

## Партиционирование

`raw_findings` и `audit_log` разделены по месяцам, `epss_history` — по дате набора с месячными партициями. Диапазоны позволяют планировщику исключать неподходящие партиции при фильтре по ключу времени и обслуживать историю отдельными частями. Они не заменяют индексы внутри частей и не ускоряют автоматически запрос без подходящего временного условия.

Нормализованная таблица `findings` не партиционирована. Штатный импорт не записывает `raw_findings`, поэтому её партиционирование не находится на основном пути записи импортируемых находок. Создание будущих партиций автоматизировано только для аудита, с ограничениями календарного расчёта. Подробности и буквальные границы — в [схеме БД](Система-Схема-базы-данных).

## Materialized views и кэш

| Объект | Фактическое применение |
|---|---|
| `dashboard_stats` | Создаётся и обновляется, но основные счётчики текущего дашборда читаются прямыми запросами к `findings` |
| `enrichment_coverage` | Используется для глобального покрытия; покрытие доступных пользователю проектов считается прямым запросом |
| `finding_scores` | Обычная таблица, а не materialized view; оценка вычисляется при обогащении |
| Redis-кэш дашборда | Только глобальная статистика администратора, TTL 60 секунд; пользовательская статистика ограничена проектами и этим кэшем не обслуживается |

Обновление materialized views выполняется каждые пять минут с `CONCURRENTLY`. Оно позволяет читать представление во время обновления, но само обновление потребляет ресурсы PostgreSQL. Выполняется пересчёт представления, а не инкрементальное обновление только изменившихся групп кодом приложения.

Представление покрытия может отставать от текущего количества находок, а глобальный результат дополнительно кэшируется. Разные показатели дашборда поэтому не обязательно соответствуют одному снимку времени. При оценке задержки данных необходимо отделять время импорта, обогащения, обновления представления и срок кэша.

## Асинхронная обработка и запись

Redis Stream выносит обогащение из времени обычного ответа импорта, но не уменьшает общий объём работы. Несколько обработчиков параллельно читают локальные справочники и записывают результаты. Каждый проход содержит отдельные запросы по находке и её идентификаторам; это не одна пакетная SQL-операция на весь отчёт.

Ручной импорт сохраняет находки по одной. CI-загрузка также выполняет UPSERT и запись связи для каждой находки, но в общей транзакции скана. Большой отчёт удерживает транзакцию и потребляет память во время разбора. Multipart может использовать временные файлы, однако затем содержимое отчёта всё равно читается в `[]byte`, а парсер возвращает массив находок. Это не потоковый разбор с постоянным потреблением памяти.

В синхронизации EPSS применяется иной путь: `CopyFrom` во временную staging-таблицу, затем SQL-вставка/обновление текущих значений и истории одной транзакцией. Условия `IS DISTINCT FROM` исключают ненужные обновления неизменившихся значений. Этот механизм не следует приписывать всем парсерам и всем синхронизаторам.

Пул `pgxpool` разделяет подключения между HTTP и фоновыми задачами. Рост числа обработчиков без учёта пула, памяти и IO может увеличить ожидание запросов. В сервере число обработчиков фиксировано при запуске; автоматического масштабирования по lag нет.

Redis используется и как кэш, и как очередь. Отсутствие очистки stream после XACK означает рост истории сообщений. Политика `allkeys-lru` в Compose не выделяет очередь в отдельную защищённую от вытеснения область. Повторная обработка Pending и ограничения доставки описаны в [обогащении](Система-Обогащение).

## Виртуализация интерфейса

Страница находок выбирает `FlatFindingsTable` для плоского режима и `GroupedFindingsTable` для группового. Плоская таблица объединяет уже загруженные страницы TanStack Query и использует `useVirtualizer`: в DOM попадают видимые строки и запас вокруг них. При приближении к концу списка запрашивается следующая страница. Аналогичная виртуализация есть в журнале аудита.

Это уменьшает число DOM-элементов и стоимость отрисовки длинного списка. Однако уже полученные данные остаются в клиентском состоянии; виртуализация не ограничивает память браузера размером видимой области и не сокращает серверный `COUNT(*)`. Групповая таблица в текущем компоненте не использует `useVirtualizer`; переносить на неё свойства плоского режима нельзя.

## Границы выводов о масштабе

| Наблюдаемая нагрузка | Где искать ограничение |
|---|---|
| Медленная страница при небольшом `limit` | Подсчёт total, фильтры, соединения, сортировка и план SQL |
| Растущий lag или Pending | Скорость SQL-обогащения, ошибки отдельных заданий и отсутствие периодического перехвата Pending |
| Долгий импорт | Разбор отчёта целиком, последовательные записи и длительность транзакции CI |
| Устаревшие показатели | Локальная копия источника, сохранённая оценка, materialized view и кэш — разные этапы |
| Рост памяти браузера | Накопленные страницы данных, не только число отрисованных строк |

В репозитории есть код нагрузочных сценариев, но само его наличие не подтверждает результат конкретного развёртывания. Страница описывает реализованные механизмы и ограничения, а не норматив производительности. Операционные показатели приведены в [мониторинге и логах](Администратор-Мониторинг-и-логи).
