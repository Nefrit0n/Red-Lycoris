# Разработка-Добавление-парсера

Парсер преобразует один формат отчёта в `[]domain.Finding`. Детектор проверяет зарегистрированные парсеры по порядку и выбирает первый, чей `CanParse` вернул `true`. Поэтому признаки формата должны быть достаточно точными, а порядок регистрации — осознанным.

## Процедура

1. Изучите формат отчёта и существующие парсеры в `backend/internal/parser`. Не используйте название файла или extension как единственный признак: API получает байты отчёта.

2. Добавьте тип, реализующий интерфейс:

   ```go
   type Parser interface {
       CanParse(data []byte) bool
       Parse(ctx context.Context, data []byte) ([]domain.Finding, error)
   }
   ```

   `CanParse` не должен принимать чужой формат. `Parse` возвращает понятную ошибку при повреждённых данных и не должен паниковать на недоверенном отчёте.

3. Заполните общую модель. Минимально для последующей валидации нужны данные, требуемые `domain.Finding.Validate`. Проект может прийти из отчёта поддерживающего это формата, быть переопределён параметром ручного импорта или назначаться проектом токена при загрузке скана. Используйте предусмотренные поля категории: CVE/CWE и компонент для SCA, путь/строки/rule для SAST, URL и HTTP-поля для DAST, IaC-поля или данные секрета по необходимости.

4. Установите `Kind` по содержимому формата. Не подменяйте сильный содержательный признак слабой подсказкой имени сканера. Для находки категории `other` detector дополнительно применяет существующие правила определения категории и может пересчитать fingerprint.

5. Вычислите fingerprint через `domain.CalculateFingerprint`, если он не задан по действующей причине. Не изобретайте другой ключ дедупликации: правила и известные ограничения описаны на странице [дедупликации](Система-Дедупликация).

6. Для секретов не записывайте исходное значение в произвольное поле находки. Если формат содержит значение, используйте `domain.ComputeSecretFingerprint` для `SecretFingerprint` и следуйте маскированию существующих Gitleaks/TruffleHog-парсеров.

7. Зарегистрируйте экземпляр в срезе `parsers` файла `detect.go`. Разместите его до более общего парсера только если его сигнатура специфичнее; Generic остаётся последним резервным форматом.

8. Добавьте table-driven тесты успешного разбора, отрицательной идентификации, повреждённого входа и нормализации полей. Для каждой находки проверьте категорию, ключевые атрибуты и fingerprint там, где он должен быть стабилен.

Проверьте результат:

```bash
cd backend
go test ./internal/parser
```

Тесты должны пройти, а отчёт нового формата при вызове detector должен вернуть ожидаемое имя парсера, а не Generic или другой зарегистрированный парсер.

## Контрольные вопросы

| Вопрос | Почему это важно |
|---|---|
| Может ли `CanParse` распознать отчёт другого инструмента? | Первый совпавший парсер прекращает поиск |
| Стабильны ли `RuleID`, первый CVE/CWE, путь и строки? | Они влияют на fingerprint и повторный импорт |
| Не попал ли секрет в description, evidence или snippet? | Отчёт — недоверенный вход; отдельный хеш не очищает другие поля |
| Есть ли тест на пустой отчёт? | Обработчики по-разному относятся к пустому результату отдельных форматов |
| Обновлены ли документация поддерживаемых сканеров и OpenAPI, если это требуется? | Пользовательский контракт и автоматическое распознавание должны совпадать |

## Границы обработчиков импорта

Ручной импорт ограничивает тело 50 MiB и сохраняет элементы независимо, собирая ошибки по индексам. CI-загрузка принимает multipart `report`, ограничивает размер через `RL_MAX_SCAN_SIZE_MB`, сохраняет скан, находки и связи в одной транзакции. Оба пути вызывают detector, но назначают проект по-разному. Не добавляйте в парсер логику авторизации или сохранения в БД.

Проверьте результат: загрузите минимальный валидный отчёт через соответствующий путь и убедитесь, что результат содержит ожидаемое число imported/updated, а не только успешный HTTP-статус.
