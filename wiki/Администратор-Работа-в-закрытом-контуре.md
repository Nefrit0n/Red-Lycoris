# Администратор-Работа-в-закрытом-контуре

Раздел различает полностью изолированный контур и частичный доступ к внешним источникам. Наличие контейнерных образов не обеспечивает наличие свежих баз обогащения; перенос образов и перенос данных выполняются отдельно.

## Что отключает ENRICHMENT_ENABLED=false

| Функция | Поведение при `false` |
| --- | --- |
| Планировщик NVD, CPE, EPSS, KEV, БДУ, CWE, OSV | Не создаётся и не запускается |
| Маршруты `/api/v1/enrichment/sync/{source}` и `/full` | Не регистрируются |
| Обработчики Redis Stream | Продолжают запускаться и читать очередь |
| Публикация заданий после импорта | Сохраняется |
| Обогащение из таблиц PostgreSQL | Сохраняется; использует уже имеющиеся локальные данные |
| Чтение статусов и результатов обогащения | Сохраняется |
| Redis, PostgreSQL и проверки готовности | По-прежнему необходимы |

`ENRICHMENT_ENABLED=false` не является сетевым межсетевым экраном. Установите ограничения исходящего трафика отдельно. В браузере форма создания пользователя обращается к HIBP; это отдельное соединение рабочего места, не контролируемое переменной backend.

### Проверка изолированного запуска

1. Задайте `ENRICHMENT_ENABLED=false` в `.env`; эта подстановка присутствует в штатном Compose. Пересоздайте backend в окно обслуживания с тем же набором файлов, что при установке.
2. Проверьте состояние:

   ```bash
   docker inspect redlycoris-backend --format '{{range .Config.Env}}{{println .}}{{end}}' | grep '^ENRICHMENT_ENABLED='
   curl --fail --silent --show-error http://localhost:8080/readyz
   docker compose exec -T redis redis-cli XINFO GROUPS enrichment:pending
   ```

Проверка результата: окружение содержит `false`, API возвращает `status: ready`, группа `enrichment-workers` существует. Вход, просмотр и импорт остаются доступны. Отсутствие свежей внешней синхронизации ожидаемо; отсутствие внешнего трафика подтверждайте журналом сетевого контроля, а не только логами приложения.

## Подготовка и перенос образов

В корневом Compose backend и frontend собираются из исходников; postgres и redis загружаются из реестра. Для сборки нужны также базовые образы Dockerfile и зависимости Go/npm. Практичный путь для изолированного узла — собрать и проверить готовые образы на подготовительном узле, затем перенести их без повторной сборки.

### Перенос готового комплекта

1. На подключённом подготовительном узле выполните [установку и проверку сборки](Администратор-Установка-Docker-Compose) выбранной ревизии с production frontend. Зафиксируйте `git rev-parse HEAD` и ответ `/api/v1/version`. Не используйте dev-образ frontend для эксплуатационного комплекта.
2. В каталоге работающей подготовительной установки получите идентификаторы образов и назначьте транспортные теги. При наличии overlay используйте тот же набор файлов Compose:

   ```bash
   docker compose images
   docker image tag "$(docker compose images -q backend)" redlycoris/backend:transfer
   docker image tag "$(docker compose images -q frontend)" redlycoris/frontend:transfer
   docker image save -o redlycoris-images.tar redlycoris/backend:transfer redlycoris/frontend:transfer postgres:16-alpine redis:7-alpine
   sha256sum redlycoris-images.tar
   ```

   Перед сохранением убедитесь, что имена тегов PostgreSQL и Redis соответствуют именно проверенным образам. Тег `transfer` — локальное имя примера, не официальный образ поставщика. Не перезаписывайте им ранее подготовленный комплект без сохранения его идентификаторов.

3. Перенесите архив, контрольную сумму, исходники выбранной ревизии и используемые Compose-файлы по согласованной процедуре. Секреты целевого `.env` передайте отдельно. На целевом узле проверьте сумму и загрузите образы:

   ```bash
   sha256sum redlycoris-images.tar
   docker image load -i redlycoris-images.tar
   docker image inspect redlycoris/backend:transfer redlycoris/frontend:transfer postgres:16-alpine redis:7-alpine --format '{{.Id}} {{.Architecture}}'
   ```

4. Создайте локальный `docker-compose.transfer.yml` в редакторе:

   ```yaml
   services:
     backend:
       image: redlycoris/backend:transfer
     frontend:
       image: redlycoris/frontend:transfer
   ```

5. Подготовьте `.env`, отключите внешние синхронизации и проверьте объединённую конфигурацию. Добавьте используемый в вашем контуре security overlay, если он есть:

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.transfer.yml config --quiet
   docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.transfer.yml up -d --no-build --pull never
   curl --fail --silent --show-error http://localhost:8080/readyz
   curl --fail --silent --show-error http://localhost:8080/api/v1/version
   ```

Проверка результата: контрольные суммы совпадают, загруженные идентификаторы образов соответствуют подготовленному комплекту, запуск не запрашивает сборку или загрузку из реестра. API готов, метаданные соответствуют ревизии. Если образ отсутствует, подготовьте недостающий образ, а не снимайте сетевой запрет автоматически. Команды переноса используют [Docker save](https://docs.docker.com/reference/cli/docker/image/save/) и [Docker load](https://docs.docker.com/reference/cli/docker/image/load/).

### Внутренний реестр

1. Вместо файлового переноса назначьте проверенным образам имена согласованного внутреннего реестра и загрузите их стандартными средствами Docker. Зафиксируйте digest каждого образа.
2. В локальном overlay задайте `image` для всех сервисов на внутренние имена. Если собираете внутри контура, отдельно зеркалируйте все `FROM` из Dockerfile и зависимости Go/npm: одних runtime-образов недостаточно.
3. Выполните `docker compose ... config --images` для своего набора файлов и `docker image inspect <имя-образа>` для каждого загруженного образа.

Проверка результата: список не содержит непредусмотренных внешних реестров, digest совпадают с журналом подготовки; выполнены HTTP-проверки из предыдущей процедуры. В поставке нет автоматического скрипта зеркалирования.

## Ручной перенос баз обогащения

Синхронизаторы сохраняют данные в PostgreSQL: `nvd_cves`, `epss_scores`, `kev_catalog`, `bdu_fstec`, `osv_vulnerabilities`, `cwe_catalog`, `cpe_dictionary`; история EPSS и статусы синхронизаций хранятся отдельно. Адреса загрузок закреплены в коде. Универсального импорта скачанного ZIP/CSV/JSON как базы обогащения и настройки URL зеркала через Config нет.

Для новой изолированной установки доступен перенос всей БД из подготовленного экземпляра той же ревизии средствами резервного копирования и восстановления. Это клонирование состояния, включая пользователей, сессии, проекты и токены, а не избирательное обновление справочников. Подготовительный экземпляр должен содержать только данные, разрешённые для целевого контура.

### Первоначальное наполнение через полный перенос

1. В подготовительном экземпляре включите синхронизации и запустите нужные источники через административный интерфейс. Дождитесь завершения; проверьте ошибки отдельных экосистем OSV, а не только общий статус.
2. Остановите запись и создайте [проверенную резервную копию](Администратор-Резервное-копирование). Перенесите архив и восстановите на чистом узле по странице [восстановления](Администратор-Восстановление), с учётом её ограничений Redis и `restore.sh`.
3. На целевом узле оставьте внешнюю синхронизацию отключённой и проверьте таблицу статусов:

   ```bash
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT source, status, records_count, last_sync_at, error_message FROM sync_status ORDER BY source;"'
   ```

Проверка результата: статусы и время актуальности соответствуют перенесённой копии; приложение готово. После тестового импорта карточка находки с известным соответствием в локальной базе получает ожидаемые данные обогащения. Это не обещает обогащение любой находки: оно зависит от идентификаторов и содержимого баз.

## Частичный внешний доступ

Все перечисленные исходные URL используют HTTPS, порт 443. Таблица получена из синхронизаторов, а не только из `docs/network_requirements.md`.

| Источник | Адрес или шаблон пути |
| --- | --- |
| NVD | `https://services.nvd.nist.gov/rest/json/cves/2.0` |
| CPE | `https://services.nvd.nist.gov/rest/json/cpes/2.0` |
| EPSS, основной | `https://epss.cyentia.com/epss_scores-{дата}.csv.gz` |
| EPSS, резервный | `https://epss.empiricalsecurity.com/epss_scores-{дата}.csv.gz` |
| EPSS, резервный | `https://raw.githubusercontent.com/empiricalsec/epss_scores/main/{год}/epss_scores-{дата}.csv.gz` |
| CISA KEV | `https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json` |
| БДУ ФСТЭК | `https://bdu.fstec.ru/files/documents/vulxml.zip` |
| OSV | `https://osv-vulnerabilities.storage.googleapis.com/{экосистема}/all.zip`; имя экосистемы URL-кодируется |
| CWE | `https://cwe.mitre.org/data/xml/cwec_latest.xml.zip` |

EPSS пробует файлы за текущий и предыдущий день на перечисленных источниках. В старом сетевом документе резервные домены EPSS не указаны. Включение планировщика регистрирует все источники: переменной выбора отдельных источников в Config нет. При разрешении только части доменов ошибки остальных ожидаемы.

Адреса назначения после HTTP-перенаправлений не закреплены кодом. Согласуйте их по наблюдаемым обращениям через сетевой контроль; не расширяйте список до произвольного интернета. Для БДУ задайте `BDU_INSECURE_SKIP_VERIFY=false` и обеспечьте доверенную цепочку сертификатов.

### Прокси и дополнительные обращения

| Компонент | Ограничение |
| --- | --- |
| NVD | Собственный `http.Transport` без функции `Proxy`; установка `HTTPS_PROXY` не подтверждает использование прокси этим синхронизатором |
| БДУ | Клон стандартного транспорта с собственными TLS-настройками |
| Остальные синхронизаторы | Клиенты без собственного транспорта, используют стандартный транспорт Go |
| Compose | `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` не передаются backend автоматически |
| Форма создания пользователя | Браузер обращается к `https://api.pwnedpasswords.com/range/` для проверки пароля; не запрос backend |

Общее утверждение старого сетевого документа, что достаточно задать `HTTPS_PROXY` для backend, неполно. Проверяйте каждый источник отдельно. NTP, DNS, внутренний реестр и инфраструктура сертификатов согласуются как сервисы вашего контура, их адреса не заданы приложением.

### Проверка частичного доступа

1. Под администратором запустите один разрешённый источник в интерфейсе обогащения.
2. Проверьте `sync_status` SQL-командой выше и журнал backend: `docker compose logs --since=15m backend`.

Проверка результата: для выбранного источника получен `success`, заполнены время и число записей, отсутствуют ошибки доступа. Ответ API `202` означает только принятие запроса, не успешную синхронизацию. Сопоставьте реальные исходящие адреса с согласованным списком.
