# Администратор-Подготовка-инфраструктуры

Сначала проверьте [требования к инфраструктуре](Администратор-Требования-к-инфраструктуре). Команды ниже предназначены для оболочки Bash на Linux; выполнять их в PowerShell без адаптации не следует. Установка приложения описана на странице [Docker Compose](Администратор-Установка-Docker-Compose).

## Установка Docker

В репозитории нет установщика Docker или списка пакетов для поддерживаемых ОС. Команды `apt`, `dnf` и настройки репозиториев нельзя считать универсальной процедурой поставки.

<!-- TODO: уточнить --> Требуются проверенные команды установки Docker Engine и Compose plugin для утверждённой матрицы ОС. Процедура ниже делегирует установку пакетов инструкции Docker и не подтверждает поддержку конкретного дистрибутива Red Lycoris.

Доступ к Docker требует повышенных полномочий. В частности, членство в группе `docker` даёт полномочия уровня root; не выдавайте его обычным пользователям платформы. См. [настройку доступа Docker](https://docs.docker.com/engine/install/linux-postinstall/).

1. Выберите дистрибутив и архитектуру, согласованные для узла установки. Установите Docker Engine и Compose plugin по [инструкции Docker для выбранной ОС](https://docs.docker.com/engine/install/). Не заменяйте Compose plugin старой командой `docker-compose`.
2. Запустите службу Docker средствами выбранной ОС. Назначьте доступ к Docker только учётной записи администратора развёртывания. Последующие команды предполагают, что эта учётная запись уже имеет доступ к Docker.
3. Проверьте установку:

   ```bash
   docker version
   docker compose version
   docker info --format '{{.OSType}} {{.Architecture}} {{.DockerRootDir}}'
   ```

Проверка результата: вывод содержит версии клиента, сервера и Compose; соединение с сервером проходит без ошибки доступа. Тип контейнеров — `linux`. Путь `DockerRootDir` расположен на хранилище, выбранном для образов и локальных томов.

## Каталоги и права

Не создавайте вручную каталоги с данными PostgreSQL и Redis внутри репозитория и не назначайте им `chmod 777`: поставка использует именованные тома Docker. Исходники frontend и каталог миграций подключаются из репозитория только для чтения. У серверного образа задан пользователь `nonroot`, у production frontend — `nginx`.

1. Подготовьте отдельный каталог для исходного кода. Пример пути ниже является выбором администратора, а не обязательным путём приложения:

   ```bash
   sudo install -d -m 0750 -o "$(id -un)" -g "$(id -gn)" /srv/red-lycoris
   git clone https://github.com/Nefrit0n/Red-Lycoris.git /srv/red-lycoris
   cd /srv/red-lycoris
   ```

   Используйте пустой каталог. Если репозиторий уже подготовлен, перейдите в него и не повторяйте клонирование.

2. Зафиксируйте выбранную ревизию в журнале установки. Все дальнейшие команды выполняйте из корня этой рабочей копии:

   ```bash
   git rev-parse HEAD
   git status --short
   test -r docker-compose.yml && test -r env.example && test -d backend/migrations
   ```

3. Создайте `.env`, только если его ещё нет. Команда с `test` не перезаписывает существующий файл:

   ```bash
   umask 077
   test -e .env || cp env.example .env
   chmod 600 .env
   stat -c '%a %U:%G %n' .env
   ```

Проверка результата: ревизия определена, необходимые файлы читаются, `.env` принадлежит администратору развёртывания и имеет права `600`. Его содержимое не выводите в журнал или обращение поддержки. Именованные тома будут созданы при запуске Compose; их проверка приведена в [требованиях к инфраструктуре](Администратор-Требования-к-инфраструктуре).

## Параметры ядра и лимиты

| Область | Что задаёт поставка | Что остаётся настройкой узла |
| --- | --- | --- |
| PostgreSQL | Параметры через `postgres -c`, лимиты памяти и CPU контейнера | Параметры ядра, файловой системы, разделяемой памяти и открытых файлов |
| Redis | `maxmemory 256mb`, `allkeys-lru`, AOF, лимиты контейнера | Политика overcommit, THP, лимиты открытых файлов |
| Docker | Именованные тома, параметры журналов контейнеров | Размещение данных Docker и лимиты службы |

<!-- TODO: уточнить --> Профиль обязательных `sysctl`, `ulimit` и `shm_size` для Red Lycoris не задан и не проверен для трёх ресурсных профилей. Не применяйте произвольные числовые значения из старой инструкции как требования платформы.

Изменения `sysctl` и THP затрагивают весь узел, в том числе другие приложения. Согласуйте их до применения. Для выбора настроек компонентов используйте [системные ресурсы PostgreSQL 16](https://www.postgresql.org/docs/16/kernel-resources.html) и [администрирование Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/admin/); эти справочники не заменяют испытаний конкретной установки.

### Проверка исходного состояния

1. До запуска контейнеров снимите параметры узла:

   ```bash
   sysctl vm.overcommit_memory
   test ! -r /sys/kernel/mm/transparent_hugepage/enabled || cat /sys/kernel/mm/transparent_hugepage/enabled
   ulimit -n
   ```

2. После [установки](Администратор-Установка-Docker-Compose) проверьте фактические ограничения процессов и параметры компонентов:

   ```bash
   docker compose exec -T postgres cat /proc/1/limits
   docker compose exec -T redis cat /proc/1/limits
   docker compose exec -T redis redis-cli CONFIG GET maxmemory maxmemory-policy appendonly appendfsync
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SHOW shared_buffers; SHOW work_mem; SHOW max_connections;"'
   ```

Проверка результата: команды чтения завершаются без ошибок; зафиксированы реальные лимиты процессов, а не только оболочки администратора. Для неизменённой поставки PostgreSQL возвращает `256MB`, `16MB`, `100`; Redis — `268435456`, `allkeys-lru`, `yes`, `everysec` для соответствующих параметров. При production-запуске добавьте оба флага `-f` ко всем командам Compose.

## Часовой пояс и синхронизация времени

В Compose не заданы `TZ`, служба NTP или источник времени. Скрипт сборки формирует `BUILD_DATE` через `date -u`. Не принимайте часовой пояс интерфейса за доказательство правильного времени на сервере.

1. Настройте синхронизацию времени штатными средствами выбранной ОС с источником, принятым в организации. Не запускайте вторую службу синхронизации поверх уже работающей.
2. Зафиксируйте часовой пояс узла. Для ОС с `systemd-timedated` проверьте состояние:

   ```bash
   date -u +'%Y-%m-%dT%H:%M:%SZ'
   timedatectl status
   timedatectl show -p NTPSynchronized --value
   ```

Проверка результата: время UTC соответствует доверенному источнику, часовой пояс соответствует принятой настройке, а `NTPSynchronized` возвращает `yes`. Если ОС не использует эту службу, выполните эквивалентную проверку её штатным средством и сохраните результат. Требование использовать конкретный часовой пояс или конкретную реализацию NTP кодом не установлено.
