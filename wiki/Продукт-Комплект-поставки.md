# Продукт-Комплект-поставки

Репозиторий содержит исходный код, инструкции сборки контейнеров, конфигурации Compose, миграции и эксплуатационные скрипты. Внешние справочники обогащения загружаются при работе синхронизаторов, а не включаются готовой БД в образы приложения.

## Образы и сборка

| Компонент | Что формируется | Откуда берутся составляющие |
|---|---|---|
| Сервер приложения | Исполняемые файлы `/app/redlycoris`, `/app/admin`, `/app/healthcheck` и каталог `/app/migrations` | Локальная сборка из `backend/`; этап сборки — `golang:1.25.11-bookworm`, итоговый образ — `gcr.io/distroless/static-debian12:nonroot` |
| Интерфейс для эксплуатации | Статические файлы интерфейса и конфигурация nginx | Локальная сборка из `frontend/` на `node:20-bookworm-slim`, итоговый образ — `nginx:stable` |
| Интерфейс для разработки | Исходный код и сервер Vite | Цель `development` в Dockerfile, основа — `node:20-bookworm-slim` |
| PostgreSQL | Отдельный контейнер БД | Готовый образ `postgres:16-alpine` |
| Redis | Отдельный контейнер кэша и очереди | Готовый образ `redis:7-alpine` |

Образы без явно указанного реестра используют стандартный реестр Docker; образ distroless указан с реестром `gcr.io`. При отсутствии локального кэша сборка требует доступа к базовым образам, загрузке модулей Go и пакетов npm. Dockerfile сервера выполняет `go mod download`, Dockerfile интерфейса — `npm ci --include=optional` и сборку интерфейса.

В `backend/go.mod` директива языка — `go 1.25.0`; это не основание обещать сборку любым Go 1.25 независимо от требований зависимостей. Зависимости интерфейса задают React `^19.2.4`. Версию реально использованного Go возвращает установленный сервер — см. [историю версий](Продукт-История-версий).

## Конфигурации развёртывания

| Файл | Назначение и фактическое поведение |
|---|---|
| `docker-compose.yml` | Определяет PostgreSQL, Redis, сервер и интерфейс; сервер и интерфейс имеют секции `build`, БД и Redis — `image`; данные размещаются в именованных томах |
| `docker-compose.prod.yml` | Дополнение к основному файлу: снимает публикацию портов PostgreSQL и Redis, меняет лимиты ресурсов, выбирает сборку интерфейса `production` и убирает его монтирования исходного кода |
| `env.example` | Пример переменных для приложения и Compose; не гарантирует автоматическую передачу каждой переменной в контейнер |
| `frontend/nginx/default.conf` | Обслуживание интерфейса и проксирование `/api/` на сервер приложения |

Дополнение `docker-compose.prod.yml` не является самостоятельной полной конфигурацией и не снимает публикацию порта сервера приложения. Оно также не задаёт `ENV=production` и `COOKIE_SECURE` серверу. Наличие этих значений в `.env` само по себе не передаёт их в контейнер: для этого нужна соответствующая запись в конфигурации Compose. Поэтому имя файла не означает, что настройка безопасности завершена.

В базовом Compose при отсутствии `FRONTEND_TARGET` выбрана цель `production`, тогда как в `env.example` задано `FRONTEND_TARGET=development`. Режим после копирования примера отличается от режима с незаданной переменной.

Отдельного файла `deployments/docker-compose.prod.yml` в проверенной версии репозитория нет.

## Миграции и инструменты

| Составляющая | Назначение |
|---|---|
| `backend/migrations/` | SQL-миграции прямого и обратного направления; сервер применяет прямые миграции при старте |
| `backend/cmd/admin/` | Командный инструмент управления учётными записями; входит в образ сервера |
| `backend/cmd/seed/`, `backend/cmd/loadtest/` | Генерация тестовых данных и нагрузочные сценарии; не копируются как готовые исполняемые файлы в итоговый образ сервера |
| `scripts/build.sh` | Сборка сервисов Compose с передачей версии, коммита и времени сборки; версия по умолчанию читается из `VERSION` |
| `scripts/seed.sh` | Сборка и запуск генератора тестовых данных |
| `ops/backup/backup.sh` | Архив резервной копии PostgreSQL, необязательного снимка Redis и манифеста |
| `ops/backup/restore.sh` | Восстановление архива с остановкой сервисов приложения и пересозданием БД |
| `ops/backup/verify.sh` | Проверка архива и пробное восстановление во временные контейнеры |
| `scripts/build-third-party-licenses.ps1`, `scripts/frontend-licenses-to-md.cjs` | Подготовка сведений о лицензиях зависимостей |
| `Makefile` | Обёртки команд Compose и вспомогательных действий |

Восстановление резервной копии удаляет текущую БД перед её созданием заново. Генератор тестовых данных изменяет целевую БД. Эти инструменты не относятся к безопасным командам просмотра состава поставки.

Имена целей Makefile не заменяют проверку их реализации: `migrate` запускает ещё один экземпляр серверного исполняемого файла, а не отдельный режим миграций; `sync` отправляет запросы без учётных данных, хотя соответствующие маршруты защищены. Отдельного `scripts/sync-all.sh` в проверенной версии нет. Рабочие процедуры относятся к руководству администратора.

## Публикация через CI

Процесс CI настроен на сборку и публикацию `ghcr.io/nefrit0n/red-lycoris/backend` и `ghcr.io/nefrit0n/red-lycoris/frontend`. Он задаёт теги версии, `latest` и теги коммита, подписывает образы, формирует SBOM в форматах CycloneDX и SPDX и прикладывает артефакты к выпуску GitHub. Это описание конфигурации процесса, а не подтверждение успешного выпуска конкретного тега.

Поставляемые Compose-файлы не ссылаются на эти готовые образы для сервисов приложения: стандартный путь в них — локальная сборка. Для использования опубликованных образов требуется отдельная конфигурация с выбранными тегами или дайджестами. Наличие стадии `deploy` в CI не означает установки на ваш сервер: эта стадия выводит сводку выпуска.

Источник: [https://github.com/Nefrit0n/Red-Lycoris/blob/main/.github/workflows/ci.yml](https://github.com/Nefrit0n/Red-Lycoris/blob/main/.github/workflows/ci.yml).
