# Администратор-Обновление

Обновление выполняется с перерывом обслуживания. Backend применяет миграции при каждом старте до открытия HTTP-порта. Отдельного безопасного режима «только миграции» у серверного бинарного файла нет; цель `make migrate` запускает ещё один экземпляр сервера.

## Подготовка

1. Зафиксируйте работающую ревизию, версию схемы, образы и набор Compose-файлов. Пример для корневого production overlay:

   ```bash
   export COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml
   git status --short
   git rev-parse HEAD
   curl --fail --silent --show-error http://localhost:8080/api/v1/version
   docker compose images
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version, dirty FROM schema_migrations;"'
   ```

   Добавьте ваши локальные overlay. Не заменяйте текущую рабочую копию, если есть несохранённые изменения; сохраните их отдельно согласованным способом. Не выполняйте `git reset --hard` или `make clean` для подготовки.

2. Выберите конкретную целевую ревизию и изучите изменения кода конфигурации, Dockerfile и SQL-миграций относительно текущей. Не считайте CHANGELOG достаточным подтверждением совместимости.
3. Сохраните старые образы под отдельными именами и вне узла установки, вместе с исходниками и конфигурацией. До начала работ выполните [резервное копирование](Администратор-Резервное-копирование) и пробное [восстановление](Администратор-Восстановление) на отдельном узле. Проверьте ограничения Redis: одного сообщения об успешном `verify.sh` недостаточно.

Проверка результата: есть проверенный путь возврата данных, известны точные идентификаторы старой и новой сборок, текущая схема не dirty. Если восстановление для выбранной конфигурации не подтверждено, не начинайте обновление рабочей установки.

## Смена ревизии и сборка

1. Закройте внешний приём запросов. Остановите приложение, оставив хранилища доступными:

   ```bash
   docker compose stop frontend backend
   docker compose ps
   ```

2. После остановки записи создайте окончательную копию текущего состояния. При использовании процедуры копирования не выполняйте её шаг повторного запуска приложения до завершения обновления.
3. Переключите исходники на утверждённый тег или commit. Следующий ввод не выбирает версию автоматически:

   ```bash
   read -r -p 'Целевой тег или commit: ' TARGET_REVISION
   test -n "$TARGET_REVISION"
   git rev-parse --verify "$TARGET_REVISION^{commit}"
   git switch --detach "$TARGET_REVISION"
   git rev-parse HEAD
   ```

   Ревизия должна уже присутствовать локально; в закрытом контуре перенесите её заранее. Сохраните прежний каталог, имя проекта Compose и привязки томов. Согласуйте изменения локальных overlay с новой поставкой.

4. Соберите образы с метаданными новой ревизии либо загрузите заранее проверенный комплект:

   ```bash
   export VERSION="$(tr -d '[:space:]' < VERSION)"
   export COMMIT="$(git rev-parse --short HEAD)"
   export BUILD_DATE="$(date -u +'%Y-%m-%dT%H:%M:%SZ')"
   docker compose config --quiet
   docker compose build backend frontend
   ```

Проверка результата: остановлены именно прикладные сервисы; ревизия соответствует плану, конфигурация корректна, сборка завершена без ошибок. В закрытом контуре вместо сборки используйте [перенос образов](Администратор-Работа-в-закрытом-контуре). Обновление приложения не является разрешением одновременно менять основные версии PostgreSQL или Redis.

## Запуск и применение миграций

Предупреждение: следующая команда запускает миграции на существующей БД. После изменения схемы прежний образ может оказаться несовместимым; простой перезапуск старого контейнера не является откатом данных.

1. Пересоздайте только backend, не меняя контейнеры хранилищ:

   ```bash
   docker compose up -d --no-deps --no-build --force-recreate backend
   docker compose logs --tail=150 backend
   ```

2. Дождитесь готовности и проверьте схему:

   ```bash
   curl --fail --silent --show-error http://localhost:8080/readyz
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version, dirty FROM schema_migrations;"'
   printf '%s\n' backend/migrations/*.up.sql | sort
   ```

3. После успешного результата запустите новый frontend:

   ```bash
   docker compose up -d --no-deps --no-build --force-recreate frontend
   curl --fail --silent --show-error http://localhost:3000/api/v1/version
   ```

Проверка результата: backend готов, `dirty=f`, номер схемы соответствует набору миграций выбранной ревизии. Версия через frontend возвращает JSON с ожидаемым commit. При уровне `warn` сообщения INFO о применении миграций не видны, поэтому отсутствие строки `migrations applied` само по себе не доказывает ошибку.

## Неуспешная миграция

1. Не открывайте внешний доступ. Остановите backend, чтобы исключить повторные запуски:

   ```bash
   docker compose stop backend
   docker compose logs --tail=200 backend
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version, dirty FROM schema_migrations;"'
   ```

2. Сопоставьте ошибку с конкретным `.up.sql`. Возможны ошибки подключения, отсутствующий файл, недостаточные права, нарушение ограничений данных и частичное выполнение SQL. Например, миграция `028` отклоняет дубли имён групп без учёта регистра и ссылки `project_access` на отсутствующих субъектов.
3. При `dirty=t` не меняйте значение вручную и не выполняйте `force` без установленного состояния каждого оператора миграции. Выберите либо восстановление проверенной предобновительной копии, либо отдельно проверенный план исправления конкретной миграции. Для ошибки до начала миграций устраните причину подключения/конфигурации и повторите запуск только после проверки схемы.

Проверка результата: определены номер, стадия и причина ошибки, приложение не пишет в неопределённую схему. Продолжать обновление можно только после возвращения схемы в проверенное состояние; изменение одной отметки dirty не является исправлением.

## Откат

Предупреждение: восстановление предобновительной копии удаляет изменения, появившиеся после её создания. Зафиксируйте допустимость этой потери до восстановления.

1. Оставьте приложение остановленным. Если миграции меняли БД или их состояние неизвестно, восстановите предобновительную копию по [процедуре восстановления](Администратор-Восстановление), включая согласование состояния Redis.
2. Верните сохранённую ревизию исходников и прежние runtime-образы. При смене тегов задайте точные старые `image` в локальном overlay и проверьте `docker compose config --images`. Не запускайте старый backend на новой схеме в предположении обратной совместимости.
3. Запустите сохранённый комплект без сборки и загрузки новых образов:

   ```bash
   docker compose up -d --no-build --pull never backend frontend
   curl --fail --silent --show-error http://localhost:8080/readyz
   curl --fail --silent --show-error http://localhost:8080/api/v1/version
   ```

Проверка результата: возвращены именно прежние commit, схема и контрольные данные; отсутствуют незавершённые миграции. Откат только образов допустим лишь при отдельно подтверждённой совместимости с фактической схемой, а не по наличию `.down.sql`.

## Приёмка после обновления или отката

1. Выполните проверки [мониторинга](Администратор-Мониторинг-и-логи): готовность, состояние БД/Redis, версия и доступность метрик.
2. Войдите контрольными пользователями, проверьте проектные права, список находок, карточку и историю. Выполните согласованный тестовый импорт и проверьте его результат. Для включённого обогащения проверьте очередь и статусы источников.
3. Проверьте внешнюю HTTPS-точку и cookie по [сетевому чек-листу](Администратор-Безопасная-сетевая-конфигурация).

Проверка результата: функциональные проверки соответствуют ожидаемым данным и правам, версия зафиксирована в журнале работ. Только после этого возобновите внешний приём данных.
