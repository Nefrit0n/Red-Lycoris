# Администратор-Первичная-настройка

Выполните настройку после [проверки установки](Администратор-Установка-Docker-Compose), до предоставления доступа пользователям. Адрес frontend ниже обозначает адрес вашей установки; при локальном запуске это `http://localhost:3000`.

## Первоначальный администратор

Backend создаёт первоначального администратора после миграций, только если таблица `users` пуста. Если в ней есть хотя бы один пользователь, bootstrap пропускается: изменение переменных окружения не сбрасывает пароль и не создаёт второго администратора.

| Переменная | Использование |
| --- | --- |
| `BOOTSTRAP_ADMIN_EMAIL` | Адрес создаваемой учётной записи; пробелы по краям удаляются, регистр приводится к нижнему |
| `BOOTSTRAP_ADMIN_PASSWORD` | Первоначальный пароль; задайте до первого запуска |
| `BOOTSTRAP_ADMIN_FULL_NAME` | Отображаемое имя |
| `BOOTSTRAP_ADMIN_FORCE_PASSWORD_CHANGE` | Читается конфигурацией и выводится в журнал bootstrap, но не устанавливает требование смены пароля в БД |

Важно: в текущей реализации `ensureBootstrapAdmin` не вызывает `SetMustChangePassword`. Поэтому значение `true` в окружении и в сообщении журнала не гарантирует принудительную смену bootstrap-пароля. Выполните смену самостоятельно сразу после первого входа. Пароль хранится как хеш Argon2id, а не bcrypt.

### Вход и проверка учётной записи

1. Откройте frontend и войдите с адресом и паролем, заданными перед запуском. Не используйте данные из `env.example` без замены.
2. В консоли браузера на странице приложения выполните читающий запрос:

   ```javascript
   await fetch('/api/v1/auth/me').then(async response => {
     const body = await response.json();
     return {
       status: response.status,
       email: body.data?.user?.email,
       globalRole: body.data?.user?.global_role
     };
   })
   ```

Проверка результата: HTTP `200`, ожидаемый адрес и `globalRole: 1`. Если учётная запись не создана, проверьте журнал backend и наличие пользователей в БД; не удаляйте данные для повторного bootstrap.

## Смена первоначального пароля

Смена пароля отзывает существующие сессии пользователя и создаёт новую сессию для текущего входа. Предупредите пользователя о завершении других его сеансов до выполнения операции.

1. Откройте путь `/auth/change-password` на адресе frontend, даже если автоматического перенаправления не произошло.
2. Введите текущий пароль и новый уникальный пароль. Форма смены вызывает `POST /api/v1/auth/change-password` с полями `current_password` и `new_password`. Сервер проверяет минимум 8 символов после удаления краевых пробелов; этот порог отличается от создания пользователя администратором. Не используйте минимальный порог как рекомендацию по стойкости пароля.
3. Отправьте форму. Затем выйдите и проверьте вход с новым паролем.
4. На узле установки проверьте запись учётных данных. Используйте `dc` из [инструкции установки](Администратор-Установка-Docker-Compose):

   ```bash
   dc exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT u.email, c.user_id IS NOT NULL AS credentials_present, c.must_change, c.password_set_at FROM users u LEFT JOIN user_credentials c ON c.user_id = u.id ORDER BY u.email;"'
   ```

Проверка результата: в сетевой панели браузера запрос смены возвращает HTTP `200` и `data.status: "password changed"`. Для изменённой учётной записи SQL показывает `credentials_present = t`, `must_change = f`, время установки пароля заполнено. Повторный вход с новым паролем успешен; запрос `/api/v1/auth/me` снова возвращает HTTP `200`. Не выводите хеши паролей и значения cookie для проверки.

| Ответ при смене пароля | Причина |
| --- | --- |
| HTTP `400`, `VALIDATION_ERROR` | Некорректное тело, пустой или слишком короткий новый пароль |
| HTTP `403`, `INVALID_CURRENT_PASSWORD` | Текущий пароль не прошёл проверку |
| HTTP `401` | Нет действующей аутентифицированной сессии; выполните вход повторно |

Не подменяйте эту процедуру изменением `BOOTSTRAP_ADMIN_PASSWORD`: существующая учётная запись от этого не изменится. При этом Compose продолжает требовать непустую переменную даже для уже инициализированной установки.

## Первый проект

1. Откройте раздел проектов и нажмите «Создать проект».
2. На шаге «Основы» задайте название, проверьте идентификатор проекта и выберите шаблон. Форма проверяет длину названия от 3 до 64 символов. Описание и теги заполните при необходимости.
3. На шаге «Источник» выберите «Пропустить и настроить позже». Это позволяет проверить создание проекта без подключения источника. Само наличие вариантов репозитория и CI в мастере не означает запуска сканеров платформой.
4. На шаге «Команда и SLA» проверьте владельца, видимость и значения SLA. Для первого проекта оставьте владельцем первоначального администратора; приглашения и команду можно не задавать. Нажмите «Создать проект».
5. Проверьте ответ создания в сетевой панели и выполните читающую проверку в консоли браузера:

   ```javascript
   await fetch('/api/v1/projects').then(async response => ({
     status: response.status,
     body: await response.json()
   }))
   ```

Проверка результата: запрос `POST /api/v1/projects` возвращает HTTP `201` с `data.id`; интерфейс открывает созданный проект. В ответе списка присутствует его имя и идентификатор. Для проверки проекта вне первой страницы списка выполните `GET /api/v1/projects/<идентификатор>` через браузерную консоль; ожидаются HTTP `200` и тот же `data.id`. Создателю назначается роль администратора проекта.

## Создание пользователей

Административная форма принимает роль и существующие группы, но не заменяет назначение доступа к конкретному проекту. Не выдавайте глобальную роль администратора ради доступа к одному проекту. Значение `role_key=admin` создаёт глобального администратора; остальные допустимые значения не дают этот глобальный признак.

Поле отправки учётных данных по почте присутствует в запросе, но обработчик создания не выполняет отправку. Передайте первоначальные данные пользователю по принятому в организации защищённому каналу. Не рассчитывайте на письмо от платформы.

1. Под учётной записью администратора откройте `/admin/access/users` и форму создания пользователя.
2. Задайте адрес, отображаемое имя, первоначальный пароль и роль. Сервер требует пароль не короче 12 символов, запрещает совпадение с адресом и значения из встроенного списка распространённых паролей. Не включайте отправку письма как способ передачи доступа.
3. Если группы уже существуют, выберите нужные в форме; ограничения описаны ниже. Сохраните пользователя и вернитесь к списку пользователей для проверки.
4. Передайте данные пользователю. При первом входе пользователь должен выполнить [смену пароля](Администратор-Первичная-настройка#смена-первоначального-пароля). Для созданных этим обработчиком пользователей устанавливается `must_change = true`; защищённые маршруты возвращают HTTP `401` с кодом `FORCE_PASSWORD_CHANGE`, пока требование не снято. Клиент обрабатывает этот ответ переходом на форму смены.
5. Проверьте создание через запрос в консоли браузера администратора, заменив адрес в примере:

   ```javascript
   await fetch('/api/v1/admin/users?q=' + encodeURIComponent('user@example.org'))
     .then(async response => ({ status: response.status, body: await response.json() }))
   ```

Проверка результата: создание возвращает HTTP `201`, читающий запрос — HTTP `200` и запись с нужным адресом. До первой смены пароля запрос к `user_credentials` из предыдущего раздела показывает для неё `must_change = t`, после успешной смены — `f`. Обработчик создаёт пользователя со статусом `pending` и `is_active=true`; не ожидайте отдельного письма активации или автоматического перехода статуса в `active` от самой смены пароля.

### Назначение доступа к проекту

1. Откройте созданный проект и вкладку «Участники».
2. Нажмите «Добавить участника», выберите созданного пользователя и подтвердите. Эта форма добавляет участника с ролью «Триаж» (`1`); при необходимости измените роль в списке после добавления.
3. Выполните проверку в консоли браузера администратора, заменив идентификатор проекта:

   ```javascript
   await fetch('/api/v1/projects/<идентификатор>/members')
     .then(async response => ({ status: response.status, body: await response.json() }))
   ```

Проверка результата: HTTP `200`, в `data` есть добавленный пользователь с выбранной ролью. Дополнительно выполните вход этим пользователем после смены пароля и убедитесь, что проект доступен. Добавление в список пользователей без этой проверки не подтверждает доступ к проекту.

## Группы: реализованные границы

В схеме БД есть `groups` и `user_groups`. Реализованы чтение списка `GET /api/v1/admin/groups` и назначение существующих групп при создании пользователя. Маршрута создания группы в `router.go` и законченной формы её создания нет. Поэтому выполнить штатное заведение первой группы через текущие API и интерфейс нельзя; прямые вставки SQL не являются процедурой администрирования этой поставки.

Команды проекта (`teams`) — другая сущность. Создание команды в мастере проекта не создаёт группу доступа. Для первичной настройки используйте явное назначение участников проекта.

### Проверка доступных групп

1. Под администратором выполните в консоли браузера:

   ```javascript
   await fetch('/api/v1/admin/groups?limit=10')
     .then(async response => ({ status: response.status, body: await response.json() }))
   ```

2. Если группы есть, сопоставьте их идентификаторы с вариантами в форме создания пользователя. Если список пуст, продолжите первичную настройку без групп.

Проверка результата: HTTP `200` и поле `data` со списком; пустое значение списка не является ошибкой установки. Наличие групп в ответе не подтверждает реализацию назначения проектных прав через группы.
