# Система-Обогащение

Обогащение состоит из двух независимых процессов: синхронизации внешних справочников в PostgreSQL и применения локальных данных к находкам. Обновление справочника не отправляет автоматически все связанные находки на повторное обогащение.

## Источники и интервалы

Интервалы заданы при регистрации синхронизаторов в `cmd/server/main.go`. Это интервалы ticker от запуска процесса, а не календарное расписание. Немедленная первая синхронизация при старте планировщика не выполняется.

| Источник | Адрес или шаблон адреса в коде | Интервал | Локальное хранение |
|---|---|---|---|
| NVD | `https://services.nvd.nist.gov/rest/json/cves/2.0` | 2 часа | `nvd_cves` |
| EPSS | `https://epss.cyentia.com/epss_scores-{date}.csv.gz`; резервные источники ниже | 24 часа | `epss_scores`, `epss_history` |
| CISA KEV | `https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json` | 6 часов | `kev_catalog` |
| БДУ ФСТЭК | `https://bdu.fstec.ru/files/documents/vulxml.zip` | 7 суток | `bdu_fstec` |
| OSV | `https://osv-vulnerabilities.storage.googleapis.com/{ecosystem}/all.zip` | 24 часа | `osv_vulnerabilities` |
| CWE | `https://cwe.mitre.org/data/xml/cwec_latest.xml.zip` | 30 суток | `cwe_catalog` |
| CPE | `https://services.nvd.nist.gov/rest/json/cpes/2.0` | 7 суток | `cpe_dictionary` |

Для EPSS предусмотрены также `https://epss.empiricalsecurity.com/epss_scores-{date}.csv.gz` и `https://raw.githubusercontent.com/empiricalsec/epss_scores/main/{year}/epss_scores-{date}.csv.gz`. Перечень экосистем OSV задан в синхронизаторе; размер и длительность загрузки зависят от этих архивов.

Планировщик ограничивает один запуск синхронизации четырьмя часами и не допускает одновременного запуска одного источника **в пределах процесса**. Ручной запуск использует тот же механизм. Распределённой блокировки между экземплярами сервера нет. HTTP-клиенты источников могут иметь собственные более короткие таймауты; например, у OSV — 30 минут.

`RunSync` записывает в `sync_status` состояние `running`, затем `success` либо `error`, длительность и сведения об ошибке. Если запись статуса сама не удалась, таблица может не отражать фактическое завершение; в частности, после отмены контекста запись ошибки использует тот же контекст.

### Отключение внешней синхронизации

При `ENRICHMENT_ENABLED=false` сервер не создаёт планировщик источников и не регистрирует его маршруты ручной синхронизации. При этом consumer Redis, локальное обогащение и обновление materialized views продолжают работать. Наличие локальной копии справочника позволяет применять её без внешнего запроса из `EnrichFinding`.

Следовательно, этот флаг не означает «не рассчитывать priority» и не является сетевым межсетевым экраном. Подготовка закрытого контура описана в [руководстве администратора](Администратор-Работа-в-закрытом-контуре).

## Сопоставление находки

| Источник | Фактическое сопоставление и результат |
|---|---|
| NVD | По CVE; описание, CVSS, ссылки, CWE и сведения CPE. Проверка CPE использует данные NVD и компонент находки |
| EPSS | По CVE; текущая оценка, percentile, история за последние 90 дней и тренды |
| KEV | По CVE; срок, срочность, ransomware, требуемое действие |
| БДУ | По вхождению CVE в массив `bdu_fstec.cve_ids`; дополнительные атрибуты БДУ |
| OSV | Сначала пересечение CVE и aliases. При отсутствии результата — экосистема, выведенная из source/kind/component, и точное имя пакета; такие записи помечаются `package_fallback` |
| CWE | По CWE самой находки; описание, цепочка родителей, меры и дополнительные классификации |
| CPE dictionary | Синхронизируется отдельно; `EnrichFinding` не создаёт самостоятельный снимок источника `cpe` из этой таблицы |

Резервное сопоставление OSV не проверяет установленную версию по уязвимому диапазону и может возвращать связанные с пакетом, но неприменимые к находке advisory. Данные об исправлении в таком результате могут повлиять на бонус приоритета. Для NVD с несколькими CVE выбор итогового CVSS также имеет ограничение, описанное в [приоритизации](Система-Приоритизация).

Снимки сохраняются по ключу `(finding_id, source)`. Если при следующем проходе совпадений источника нет, старый снимок не удаляется автоматически. Снимки и оценка пишутся отдельными SQL-операциями, не одной общей транзакцией. Часть ошибок чтения и записи снимков только журналируется, поэтому успешный возврат функции не гарантирует полноту всех источников.

## Redis Streams

| Параметр | Значение и поведение |
|---|---|
| Stream | `enrichment:pending` |
| Consumer group | `enrichment-workers` |
| Создание группы | `XGROUP CREATE ... 0 MKSTREAM`; существующая группа сохраняется |
| Сообщение | Поле `finding_id` со строковым UUID |
| Публикация | `XADD` через Redis pipeline, без ограничения длины stream |
| Обработчики | Сервер запускает три goroutine с именами `worker-0`, `worker-1`, `worker-2` |
| Новые сообщения | `XREADGROUP` с `>`, до 10 сообщений за чтение, блокировка до 5 секунд |
| Старые неподтверждённые | При старте каждого consumer вызывается `XREADGROUP` с `0` для его собственного Pending Entries List |

### Когда создаются задания

| Событие | Действие |
|---|---|
| Ручной импорт | В очередь отправляются только новые находки после записи |
| Успешная CI-загрузка | После commit отправляются все находки скана, включая повторные |
| Ручное обогащение одной находки | Публикуется ID; при ошибке Redis обработчик пробует выполнить обогащение синхронно |
| Массовое `enrich-all` | Отдельная фоновая обработка без Redis: выбираются только находки без `finding_scores`, порциями до 100 |
| Завершение синхронизации источника | Справочник обновлён; автоматической рассылки заданий на ранее оценённые находки нет |

Транзакция CI не включает Redis. Если `XADD` после commit не удался, импорт остаётся успешным, а ошибка публикации записывается в лог. Автоматического периодического запуска `enrich-all` в сервере нет, несмотря на упоминание периодичности в комментарии обработчика сканов.

### Подтверждение и повторная обработка

| Результат обработки сообщения | XACK | Последствие |
|---|---|---|
| `EnrichFinding` вернула `nil` | Выполняется | Сообщение убирается из Pending группы; это не гарантия полноты всех снимков |
| `EnrichFinding` вернула ошибку | Не выполняется | Сообщение остаётся Pending |
| Нет строкового `finding_id` или UUID некорректен | Выполняется после предупреждения | Некорректное сообщение не повторяется |
| Ошибка самого XACK | Записывается в лог | Успешно обработанное сообщение может остаться Pending и обработаться повторно |

Таким образом, формулировка «XACK только при успехе» верна лишь для корректных заданий, дошедших до `EnrichFinding`. Некорректные сообщения подтверждаются намеренно отдельной веткой кода.

XACK не удаляет запись из самого stream. Код не выполняет `XTRIM`/`XDEL`; длина stream не равна числу необработанных заданий. При планировании хранения учитывайте и доставленные записи. В поставляемом Compose Redis одновременно обслуживает кэш и очередь с политикой `allkeys-lru`; эта конфигурация не изолирует очередь от вытеснения ключей.

## Границы автоматического восстановления

Восстановление ограничено чтением **собственного** Pending при старте consumer. Периодического `XAUTOCLAIM`/`XCLAIM` и передачи заданий от недоступного consumer другому в коде нет. Ошибка при обычной обработке нового сообщения оставляет его Pending, но тот же работающий consumer не возвращается к нему по таймеру.

При повторном запуске с прежним именем consumer читает свои Pending до перехода к новым сообщениям. Постоянно ошибающееся задание может задерживать этот переход: лимита попыток, отдельной очереди ошибок и задержки между повторениями в `processPending` нет. Имена consumer одинаковы на разных экземплярах сервера, поэтому запуск дополнительных реплик не создаёт автоматически корректную независимую группу исполнителей.

Успех записи оценки и XACK не атомарны. Повторная обработка возможна, а потеря задания возможна между commit PostgreSQL и публикацией Redis. Эта реализация не обеспечивает сквозную гарантию «ровно один раз».

Практические проверки Pending и ошибок приведены в [диагностике](Администратор-Диагностика). Актуальность справочника, наличие строки оценки и отсутствие Pending — разные признаки состояния, их нельзя заменять одним статусом «обогащение успешно».
